4. 콘 SD카드 마운트 — CH422G 통합 + 스키매틱 발굴
   - 콘 보드(Waveshare ESP32-S3-Touch-LCD-4.3B)의 SD는 SPI모드(IO11/12/13=MOSI/SCK/MISO),
     CS는 일반 GPIO가 아니라 CH422G I2C 익스팬더의 EXIO4 — 레포에 스키매틱 파일이 없어서
     사용자가 채팅에 직접 붙여넣어준 것에서 SD 핀 정보 확인. EXIO4의 정확한 비트 위치는
     처음엔 추측 안 하고 보류했다가, 레포 안 예전에 버려진 커스텀 BSP 백업 폴더
     (`_Archive/Cntl_backup_20260730_224030/bsp_ws_4_3b/`)에서 이미 검증됐던 완전한 CH422G
     드라이버(ch422g.c/.h)를 발견 — 그대로 `Cntl/components/`에 복사해 재사용.
   - 기존 `waveshare_rgb_lcd_port.c`의 즉석 매직넘버 I2C 쓰기(0x2C/0x2E/0x1E)를 이 드라이버의
     `ch422g_set_io_raw()` 호출로 교체(동일 바이트 재현, 동작 변화 없음) — 섀도우상태 소유자를
     하나로 통일(SD_CS를 별도로 추적하면 두 섀도우가 서로 덮어쓸 위험 있었음). 디스플레이/
     터치/백라이트 전부 정상 확인 후("다 잘돼"), `Cntl/main/sd_storage.c` 신설 —
     `esp_vfs_fat_sdspi_mount()`, CS는 CH422G로 한 번만 LOW로 내리고 계속 유지
     (`gpio_cs=SDSPI_SLOT_NO_CS`, ESP-IDF 공식 지원 패턴, 이 SPI버스엔 SD 말고 다른 장치
     없음 확인됨). **실기 첫 시도에 바로 마운트 성공.** 화면 로그탭에도 성공/실패 표시 추가
     (사용자 지시: "그래야 네가 캡쳐 안하고 보지").

   - **위기**: 이 위젯들(테이블+버튼+라벨) 추가만으로 콘이 부팅 여러 번 실패("watchdog",
     httpd_start 실패 등) — 사용자 확인: 이 작업 이전에도 내부 RAM이 이미 7KB밖에 안
     남아있던 상태였음. 부팅 단계별로 내부 RAM 여유를 임시로 찍어서 실측한 결과:
     LCD초기화(-33.5KB, 바운스버퍼) → **LVGL 어댑터 시작(-106KB, 최대 소비)** → 위젯트리
     전체(-48.6KB, 통계탭 포함 전체 UI) → WiFi+ESP-NOW(-52.9KB) 순으로 소모, 마지막엔
     거의 0.
   - 106KB의 정체를 소스에서 확인: 써드파티 매니지드 컴포넌트
     `espressif__esp_lvgl_adapter`의 `display_manager.c`가 찢김방지(TRIPLE_PARTIAL) 모드의
     부분버퍼를 PSRAM 설정(use_psram=true)과 무관하게 **항상 내부 RAM에 하드코딩**해서
     할당(`buffer_height` 기본값 50 → 800×50×2=78KB). 이 버퍼를 그냥 PSRAM으로 옮기면
     LVGL 렌더링 자체가 매 프레임 쓰는 스크래치라 오히려 렌더링이 느려져 watchdog가
     재발할 위험이 있어서(실제로 이 접근을 다른 값으로 먼저 시도해봤다가 겪음 — 아래
     "시도했다 되돌린 것" 참고), 벤더 코드를 고치는 대신 공개 설정값인 `buffer_height`를
     10으로 낮춰서(800×10×2=16KB) 같은 내부 RAM 안에서 그냥 버퍼 자체를 줄임 —
     PSRAM 이동보다 안전한 선택. 실기 검증: 위기 시점 대비 약 50KB 회수, 화면 확인 결과
     깜빡임/찢김 없음("깜빡임 없고 부드러워") — 사용자 승인으로 이 값 확정.
   - 시도했다 되돌린 것(다시 반복하지 않도록 기록): (a) `LV_USE_CUSTOM_MALLOC`로 LVGL
     자체 malloc을 PSRAM에 강제 연결 — 링크 단계에서 실패(정적 라이브러리 스캔 순서 문제로
     심볼이 안 당겨짐), 되돌림. (b) `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL`(malloc이 내부/
     외부 RAM 중 어디를 우선할지 정하는 전역 임계값) 조정 — 0으로 낮추니 LVGL이 매 프레임
     그리기마다 새로 만드는 draw-task 스크래치까지 PSRAM으로 가서 렌더링이 watchdog
     타임아웃 넘게 느려짐, 2048로 올리니 그건 해결되지만 이번엔 SD카드 DMA버퍼 할당이
     실패(`err=0x101`) — 위젯트리(계속 남는 것)와 draw-task 스크래치(매 프레임 생성/해제)가
     같은 malloc 경로에 크기도 비슷해서 임계값 하나로 구분이 안 됨, 기본값(16384)으로
     되돌림. (buffer_height 축소가 실질적 해결책이 됨)
   - 자세한 기록: `project_cntl_stats_tab_memory_2026_09_06` 메모리 파일.

     보관하려면 결국 콘에도 대용량 저장소(SD)가 필요 — 그럴 거면 캠의 SD를 콘으로 옮기는
     게 나음(콘 보드에 이미 SD 슬롯 있음, 확인됨).
   - 초기 우려("사진은 커서 선택적으로 가져오는 게 낫다")는 사용자가 반박 — 주기촬영은
     30분~3시간마다로 드물고, 즉시촬영은 어차피 바로 가져가므로 "선택적 fetch로 대역폭
     아낀다"는 이점이 실질적으로 작음.
   - 기대 효과: 캠↔콘 통신 프로토콜 단순화(센스와 동일한 구조로 통일), 사용자 반응성
     향상(목록조회 없이 바로 결과 옴), 저장 관리 일원화.
   - 주의점: 콘에 캠이 여러 대 붙으므로 저장소를 캠별로 구분 관리해야 함.
   - 아직 설계 논의 단계 — 실제 구현(캠 SD 제거+즉시전송 프로토콜, 콘 SD 초기화+캠별
     폴더구조, 기존 LIST/FETCH 프로토콜 교체) 시작 전.

6. 밤샘 SCD41 신뢰성 테스트 — 딥슬립/라이브 둘 다 실패, 원인은 결국 하드웨어(전해콘덴서)
   - 사용자 취침 전 지시(자동테스트): 응답성 라이브(0)→30초 전환용 `/api/set_response_interval`,
     센스 재연결용 `/api/connect_sensor` 두 웹 인젝션 엔드포인트를 CNTL에 신설(핸들러는
     이미 있었으나 httpd_register_uri_handler 등록이 빠져있어서 추가), Sens/CNTL 재빌드+
     플래시 후 시나리오대로 실행.
   - **딥슬립 시나리오(응답성 30초→실제 sleep_sec=10)**: 45회 연속 정상 재부팅 사이클(~9분)
     동안 측정ID이 단 한 번도 0에서 안 올라감(전부 "중복" 캐시값 재사용) — 10분 기준
     초과로 실패 판정.
   - **라이브 재테스트(진단용)**: 리부팅 없이 한 세션에서 65회+ 연속 시도(~7분, batt_mv
     고정으로 무재부팅 확인) — 여기서도 100% 실패. 오늘 초반엔 라이브가 결국 성공했었는데
     지금은 악화된 상태.
   - **테스트 도중 별도로 발견한 신규 버그(CNTL)**: 자동테스트 스크립트가 짧은 간격으로
     반복 호출하는 도중 CNTL이 task watchdog 반복 트리거로 WiFi 이탈, 완전 응답불능 상태에
     빠짐. 원인 추적: LVGL `lv_label_set_text()`가 내용이 같아도 매번 무조건 재할당+
     무효화+TTF 재래스터링을 함(소스 직접 확인, 문자열비교 없음) — 대시보드 요약판넬/
     측정기판넬/센서목록이 1초 타이머마다 이 함수를 조건없이 호출하고 있었는데, 라이브모드
     로 센스가 1초 간격 재전송하는 동안 이게 계속 쌓여서 IDLE0가 몇 분씩 밀려 결국 WiFi까지
     끊김. **수정**: 세 곳 모두 "직전 표시문구와 같으면 호출 생략" 캐시비교 추가
     (`s_summary_row_last_text`/`s_sensor_row_last_text`/`s_sensor_todo_last_text`) — 이후
     크래시 재발 없음, 9분 캡처 안정적.
   - 원인규명 시도(소프트웨어 쪽, 전부 효과 없어서 되돌림): ① 예전 세션이 걸어둔 주기측정이
     남아있을까봐 싱글샷 init에 STOP_PERIODIC_MEASUREMENT 추가 — 효과 없음. ② 센서가
     슬립상태일까봐 WAKE_UP 추가 — 효과 없음. ③ **결정적 격리테스트**: 예전에 실제 검증됐던
     컨티뉴어스 방식(`scd41_init`+`scd41_read`)으로 임시 전환 — 자동워치독(`check_stale`)이
     발동해 STOP+재시작까지 깨끗이 수행됐는데도 ready=1이 여전히 한 번도 안 나옴. 즉 싱글샷
     이든 컨티뉴어스든 코드와 무관하게 센서가 준비완료 신호를 안 줌 — 소프트웨어 회귀가
     아니라는 뜻. 진단코드는 전부 원복, 싱글샷 설계 그대로 재확정.
   - **아침에 사용자가 실물 확인**: 센스 전압보정용으로 달아뒀던 전해콘덴서를 떼자 즉시
     정상동작. 웹서치로 근거 확인 — SCD41 데이터시트(2.3절): 센서 내부 레귤레이션이
     마이크로초 단위 과도전류(피크 최대 205mA, NDIR IR이미터 구동용)를 자체 처리하는데,
     이게 "공급단의 부하응답 특성"과 상호작용한다는 문구가 있음, 공식 권장은 "별도 LDO +
     무부하리플 30mV 이하"뿐. 전해콘덴서(高ESR, 느린 응답)가 이 내부 루프와 간섭했을
     가능성이 높음 — 세라믹(低ESR, 빠른 응답)은 계속 유지, 정상.
   - **부수적으로 확인된 별도 이슈(이산화탄소 0값 오판)**: 온습도는 정상인데 이산화탄소만
     0으로 나오는 경우가 대부분이라는 사용자 실측 보고 — CRC는 통과하지만(트랜잭션 자체는
     안 깨짐) 이산화탄소 채널 계산만 이상값을 내놓는 것으로 추정(원인 미확정, ASC가 5분
     간격 가정인데 실제는 10~12초 간격이라 보정주기가 실제보다 훨씬 빨리 도는 것과 관련
     있을 가능성 — 확인 안 된 가설). 이 처리는 아래 할일 6번 참고.
   - **추가 관찰(미해결, 검증 예정)**: 센서가 정상 동작하기 시작한 뒤로 콘 내부RAM이
     서서히(즉시 아님) 감소, 40KB까지 확인됨 — 유력 용의자는 `stats_store_append()`의
     SD카드 fopen/fclose 반복(측정이 계속 실패하던 동안엔 거의 안 불리다가, 지금 매
     측정성공마다 계속 불리기 시작함). 아직 격리검증 전.
