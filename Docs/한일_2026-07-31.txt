== 2026-07-31 작업 요약 (Cntl 4.3B 디스플레이 미표시 원인 격리 — 벤더 데모 실기 검증 성공) ==

[ 오늘 삽질한 것들 ]

1. VS Code 종료로 이전 세션(07-28~30) 기록이 통째로 유실된 채 시작
   - 코드 주석이 `project_cntl_4_3b_bsp`라는 메모리를 참고하라고 되어있는데 실제로 그 파일이
     없었음 — 진단 내용을 메모리로 남기기 전에 세션이 끊긴 것. git status/diff/커밋되지 않은
     소스 변경분만으로 "1.85C에서 4.3B로 교체 중, 커스텀 BSP로 화면 초기화 실패"까지 재구성함

2. IDF 버전 습관적 착오 — 6.0.1 계속 사용
   - 이전 세션 기록(메모리)에 6.0.1 경로가 박혀있어서 그대로 재사용했는데, 사용자가 "죽었다
     살아나면 자꾸 6.0.1을 쓰는데 앞으로도 6.0.2를 쓰도록 해"라고 직접 정정. 이미 configure까지
     끝낸 빌드 디렉터리를 지우고 6.0.2 경로(드라이브 루트 자체가 다름: `C:\esp\v6.0.2\esp-idf`)로
     다시 configure

3. git sparse-checkout 첫 시도가 작업 트리를 반쯤 깨뜨림
   - `--filter=blob:none --no-checkout`로 클론한 뒤 `git checkout origin/HEAD -- .`을 실행했더니
     sparse-checkout 필터를 무시하고 전체 경로를 시도하다 blob 누락 에러 + "삭제 대기" 상태로
     꼬임. `git reset --hard origin/HEAD`로 sparse-checkout 패턴을 존중하는 방식으로 다시 받아서
     해결

4. 벤더 데모가 설치된 IDF 6.0.2에서 그대로 컴파일 안 됨
   - README는 "IDF >= 5.5"만 요구하는데 실제로는 더 오래된 API를 씀:
     `esp_lcd_rgb_panel_config_t`의 `bits_per_pixel`/`sram_trans_align`/`psram_trans_align`
     필드가 6.0.2엔 없고, 레거시 `driver/i2c.h`로는 `esp_lcd_new_panel_io_i2c()`가 요구하는
     `i2c_master_bus_handle_t`를 만들 수 없음 — 신형 `i2c_master` API로 최소 이식

5. 컴파일 성공 후에도 실기에서 즉시 재부팅 루프
   - `esp_lcd_touch_io_i2c_config_t.scl_speed_hz = 0`(벤더 원본값, 구버전 IDF에선 "버스 기본값
     사용")이 6.0.2에서는 "invalid scl frequency"로 거부되며 `ESP_ERROR_CHECK`에서 abort.
     빌드 로그만으로는 안 보이고 실제 플래시+시리얼 모니터링으로만 잡힌 문제였음

[ 잘 찾아낸 것들 ]

1. "어디서 받을지" / "포팅 범위가 어디까지인지" 두 가지를 짐작하지 않고 AskUserQuestion으로
   먼저 확인 — GitHub에서 새로 받기 + 별도 테스트 프로젝트로 통째 포팅이라는 답을 듣고서야
   git clone 시작. 잘못 짐작했으면 네트워크/빌드 작업이 통째로 헛수고가 될 뻔함

2. 사용자가 "멈춰"라고 한 순간 진행 중이던 tool call을 즉시 중단하고 현재 상태(클론은 됐지만
   체크아웃 전)를 정확히 보고 — 다음 지시를 기다림

3. 첫 빌드 로그의 tail만 보고 "성공한 듯"으로 착각할 뻔했다가, exit code가 1이라는 걸 놓치지
   않고 전체 로그를 다시 캡처해서 "error:"로 grep — 멀티잡 인터리빙 때문에 성공 메시지
   (bootloader 서브빌드)가 마지막에 찍혀서 tail만 보면 오판하기 딱 좋은 상황이었음

4. 컴파일이 성공했다고 바로 "됐다"고 보고하지 않고 실제 플래시+시리얼 로그까지 확인 —
   그 과정에서 scl_speed_hz=0 크래시를 잡아냈음. 빌드 성공 ≠ 동작 확인이라는 걸 CAM 작업
   때 배운 그대로 다시 적용함

5. 화면이 실제로 뜨는지는 사용자가 직접 눈으로 봐야 확정되는 부분이라, 확인을 요청하는 흐름을
   유지했고 사용자가 "잘 동작한다"고 확인해줄 때까지 "고쳐졌다"고 단정하지 않음

[ 반성할 점 ]

- IDF 버전은 매번 프로파일 스크립트(`Microsoft.v<X>.PowerShell_profile.ps1`)로 재확인했어야
  하는데, 메모리에 적힌 6.0.1 명령 블록을 그대로 재사용하다 사용자 지적을 받고서야 6.0.2
  프로파일을 확인함 — 메모리 자체에 "파일이 stale해 보이면 확인하라"고 적혀있었는데 그 경고를
  안 지킴
- git sparse-checkout을 다룰 때 `checkout -- .`처럼 명시적 pathspec을 주면 sparse 필터를
  우회한다는 걸 몰라서 첫 시도가 깨짐 — `reset --hard`나 pathspec 없는 `checkout`이 sparse
  패턴을 존중한다는 걸 먼저 확인했어야 함
- 빌드 로그를 `Select-Object -Last 80`으로 잘라서 본 첫 판단이 부정확했음 — 로그 길이와
  무관하게 exit code 확인 + error 패턴 grep을 기본 습관으로 삼았어야, tail만 보고 오판할
  위험을 처음부터 없앨 수 있었음
