== 2026-09-04~09-05 작업 요약 (Cntl 신호막대 + 웹 UI합성 구현 + WAKE_HELLO/NO_MEM 버그 수정) ==

[ 한 일 ]

1. 상황판-요약 신호세기 표시
   - ESP-NOW도 RSSI 측정되는지 질문 → esp_now_recv_info_t.rx_ctrl.rssi를 recv_cb 공용
     진입점에서 무조건 캡처하도록 esp_now_hub.c에 추가.
   - 요약판넬 각 행 우측에 신호 막대 위젯 추가(숫자 대신 와이파이류 막대 표시, 사용자
     지시). 4개로 시작 → "더 늘릴 수 있나?" → 10개까지 시도 → "RSSI 흔들림 때문에
     깜빡일 것 같다"며 최종 5개로 확정.

2. 웹 UI 합성("PC 원격제어처럼") 설계+구현
   - 전날(2026-08-30) 세션에서 미룬 과제: MVC 재설계 + "웹기생"을 전체로 확대.
   - 시작 전 재검토: "더 좋은 방법이 있을까? 웹기생 말고" → 커맨드큐 방식 검토했으나
     "웹과 앱이 동시 작업하지 않아"라는 전제 때문에 불필요한 복잡도로 기각.
   - 확정 설계: 웹 입력이 실제 온디바이스 탭/팝업/확인 LVGL 이벤트 시퀀스를 그대로
     합성(탭 전환 포함) — "어차피 기생하는 거, 완전히 기생시켜서, UI를 조작하는
     것처럼 하면 어떨까?" / "그렇지. PC 원격제어처럼". 근거: 8/30 버그 둘 다 "웹이
     로직을 별도 경로로 재구현하다 원본과 어긋남"이 원인이었음 — 완전 합성은 그
     드리프트 가능성 자체를 구조적으로 없앰.
   - 출력 쪽: 연결/끊기/목록/사진 4개 기능의 성공/실패(총 8개) 모두 실제 FreeRTOS
     이벤트로 발생, 앱/웹이 각자 반응 — "폴링 하지 말고, 이벤트로 처리해(전에도 이
     짓 하다가 멈춘거야)". "연결실패"는 별도 이벤트 없이 대기함수의 자체 타임아웃이
     곧 실패 이벤트(사용자 설계: "타임아웃이 이벤트가 되는 것").
   - 메시지: 웹에 표시되는 문구도 앱과 같은 ui_str() 테이블에서 그대로 가져옴(JS는
     서버가 보낸 문구만 렌더링, 자체 하드코딩 금지).
   - 구현 범위는 이미 만들어진 3개 웹 기능(연결/끊기, 목록가져오기, 사진가져오기)만 —
     새 기능/전체 SPA는 여전히 보류.
   - 작업 시작 직전 사용자 지시대로 롤백 대비(원복 준비)부터 확인 후 진행.
   - LVGL API 삽질: `lv_event_send()`는 내부 저수준 함수라 틀렸고 `lv_obj_send_event()`가
     맞는 API. 콜백 user_data는 `lv_event_dsc_t`가 불투명 타입이라 공개API로 못 읽어서,
     위젯 자체의 범용 user_data 슬롯에 콜백 포인터/file_id를 태깅하는 방식으로 우회.

3. 리그레션 3건 발견 및 수정 (실기 테스트로 발견)
   - 사진가져오기 팝업: 새 이벤트 소비자가 팝업 자신의 200ms tick보다 먼저 READY를
     소비(ack)해버려서, 팝업이 STALLED로 오판 후 닫힘(사진은 실제로 잘 받았는데도).
   - 목록가져오기 팝업: 반대 패턴 — 팝업이 원래 자기완결형으로 소비하던 걸 새 이벤트
     소비자가 먼저 가로채서 3007(무응답) 오탐.
   - 수정: 두 팝업 다 "내가 READY를 보면 내가 직접 끝까지 소비" 패턴으로 통일, 새
     이벤트 소비자는 해당 팝업이 떠 있는 동안 양보(`fetch_popup_is_active()`/
     `list_popup_is_active()` 가드).
   - 부수적으로 사진가져오기에서 3008(선택-불일치) 오탐도 같은 원인이었음 — 위 수정으로
     같이 해결.

4. 웹 끊기 후 상황판-요약 갱신 지연 버그
   - 끊기를 눌러도 설정탭은 즉시 "연결 대기 중"으로 바뀌는데 요약판넬은 한동안
     "통신중/페어됨"으로 남아있다가 뒤늦게 "연결된 장치 없음"으로 바뀜.
   - 원인: 요약판넬의 행 재생성(dash_changed)이 mac/kind/ever_paired/name 비교에만
     걸려있고 conn_state는 안 봄 — 실제 사라짐은 esp_now_hub_get_nodes()의
     last_seen_ms 타임아웃(응답성×6, 대략 그 "30초"감)에 걸릴 때까지 미뤄짐.
   - 수정: dash_changed 비교에 conn_state 변화도 직접 포함 — 즉시 반영.

5. "캠이 광고를 늦게 시작한다"(스피커로 직접 들은 사실) 진단
   - 첫 가설(적응형대기 note_user_action 누락)은 틀렸다고 스스로 정정 — 실제로는
     "슬립 중이 아니었다"는 사용자의 직접 관찰과 안 맞음.
   - CNTL이 WAKE_HELLO에 응답 안 하는 게 아니라(esp_now_hub.c 469 — user_unpaired면
     의도적으로 무시하는 건 원래 설계), 그건 이번 케이스와 무관함을 재확인 후, 최종
     원인은 아래 6번의 WAKE_HELLO/NO_MEM 문제로 수렴.

6. 진짜 발견 — WAKE_HELLO_ACK 무응답+NO_MEM 폭주 (라이브 시리얼 캡처로 확인)
   - "누르자마자 실패"(즉시 실패) + "다른 사진 요청 중에 무관한 사진 링크가 실패로
     바뀜" 두 증상을 짐작으로 질문했다가("4번 클릭했나?" 등) 강하게 지적받음: "이따위
     질문 절대 하지 말라고 했는데 왜 자꾸 해?" → 시리얼 캡처로 전환.
   - 캡처 로그로 확정: 사진 전송 완료 직후 WAKE_HELLO가 95~100ms 간격으로 3연타 →
     `esp_now_send 실패: ESP_ERR_ESPNOW_NO_MEM` → 캠이 "페어링 끊김"으로 오판, 수초간
     재연결 폭풍.
   - 중간에 "sleep_sec=0이면 캠이 텀 없이 도는 구조"라고 잘못 짚었다가 사용자가
     `CASK_LIVE_PACE_MS=1000`(이미 있는 1초 페이싱)을 찾아내 정정 — 실제 원인은 그게
     아니라 WAKE_HELLO 자체가 100ms 타임아웃짜리 reliable 요청인데, CNTL의
     WAKE_HELLO_ACK가 반환값 체크도 없는 단발 esp_now_send라 무선큐가 잠깐 찼을 때
     조용히 실패 → 캠이 100ms 안에 못 받으면 그냥 재전송 → CNTL은 새 사이클로 착각해
     4개짜리 응답을 또 만듦 → 폭주.
   - 수정(양쪽): CNTL(esp_now_hub.c) WAKE_HELLO_ACK 전송에 반환값 체크+3회 재시도 추가.
     CAM(esp_now_cam.c) WAKE_HELLO reliable_request 타임아웃 100ms→200ms.

7. 부수 발견 — esp_now_photo_wait_cached() 전역 오류 체크 버그
   - 웹의 사진 대기함수가 file_id 구분 없이 전역 ERROR 상태만 보고 있어서, 위 6번
     같은 무관한 desync가 살짝만 스쳐도 완전히 다른 사진 요청까지 즉시 실패 처리.
   - 수정: 단일슬롯 현재 대상(s_file_id)이 기다리는 file_id와 같을 때만 실패로 인정.

8. 빌드/플래시
   - CNTL 앱파티션만 총 4회 플래시(COM19, 설정 보존).
   - CAM 1회 플래시(COM5) — 10초 슬립/짧은 깨어남 주기 때문에 포트가 순간만 보임,
     .NET SerialPort 폴링으로 깨어난 순간을 잡아서 성공.
   - 사용자 확인: "모두 다 잘동작해. 10번 정도 테스트라 적긴 하지만."

  "회상 질문"이었는데도 같은 위반으로 지적받음. 이후 시리얼 캡처로 전환한 것도
  "내가 네 테스터잖아"라는 재지적을 받음 — 재현을 시키기 전에 소스 추적을 먼저 끝까지
