== 2026-09-23 작업 요약: 브 로그 포맷 재설계 + PAIR_REQUEST 근본원인 발견/수정
   (콘 MAC이 내부 프로토콜에 들어가던 버그) ==

[ 한 일 — 브 로그 포맷 재설계 ]

1. 대화로 반복 조율해 최종 포맷 확정: 양쪽 패널 공통 순번 [00]~[99](99 다음 00으로
   순환, log_append 공통 카운터), RX(RSSI/MAC/LEN) VALUE, TX(MAC/LEN) VALUE,
   RL(S또는F/MAC/LEN/RESULT_CODE) VALUE(RLBL에서 개명 — 성격상 TX라는 점 확인됨),
   DATA rx(MAC/LEN) VALUE. MAC은 끝 6자리만, RESULT_CODE는 OK/TO/NP/FL/NM/BA/BS/E숫자
   2글자 니모닉 표(ui_screen_result_code 신설). VALUE는 data[1](msg_type)을
   ui_screen_msg_type_name()으로 디코딩한 것 — 지금 페어링 흐름에 나오는 것만 표에 있음.
2. 구현: ui_screen.c/.h(ui_screen_result_code, 순번 카운터), bridge_esp_now.c(RX/TX),
   can_link.c(RL/DATA rx) 수정. 빌드+플래시(브 COM18)+실기 시리얼 캡처로 새 포맷 확인.

[ 한 일 — PAIR_REQUEST 13/13 타임아웃 근본원인 발견/수정 ]

3. 새 로그로 확인된 사실 — ADVERTISE/ADV_ACK 교환은 정상인데 PAIR_REQUEST만 매번
   타임아웃, 캠은 계속 광고만 반복(페어링 미완료).
4. 대화로 원인 추적 — esp_now_hub.c:449, 1316에서 콘이 ADVERTISE_ACK/PAIR_REQUEST의
   hub_mac 필드에 esp_wifi_get_mac()으로 자기 WiFi MAC(ESP-NOW와 무관, 내부망 어디서도
   안 쓰이는 값)을 채워 보내고 있었음. 캠은 이 값을 그대로 믿고(esp_now_channelsync.c:
   354, esp_now_cam.c:1351) 저장해서 이후 응답(PAIR_ACK 등)을 그 주소로 보냄 — 콘은
   ESP-NOW 라디오 자체가 없어 도달 불가능한 주소라, 재시도를 아무리 해도 항상 타임아웃.
   같은 이유로 UNPAIR(esp_now_cam.c:1310)도 항상 막혀있을 것으로 보임(미검증).
5. 사용자 원칙 확정 — "콘의 MAC은 현재 코드든 향후 추가될 코드든 내부망(CAN/ESP-NOW)
   프로토콜 어디에도 들어가면 안 된다." 그렙으로 콘 전체 위반처 확인(위 2곳뿐). "필드를
   안 믿기"만 하는 절충안(브가 패치 / 콘이 브 MAC을 알아서 채움)도 검토했으나 둘 다
   "몰라도 될 걸 알아야" 하는 문제가 있어 기각 — hub_mac 필드 자체를 프로토콜에서
   제거하고, 수신측이 프레임의 실제 발신지(info->src_addr, 하드웨어가 채워주는 값이라
   항상 정확함)를 쓰는 방향으로 확정.
6. 수정 범위(공유 헤더 + 콘/캠/센스 3개 디바이스 프로젝트):
   - Common/esp_now_link.h: esp_now_advertise_ack_t/esp_now_pair_request_t에서
     hub_mac 필드 제거
   - Common/esp_now_channelsync.c:354: ack->hub_mac → info->src_addr
   - Cntl/esp_now_hub.c:449, 1316 부근: hub_mac 채우던 esp_wifi_get_mac() 호출 제거
   - CAM/esp_now_cam.c:1351: req->hub_mac → info->src_addr
   - Sens/esp_now_node_cask.c:288, esp_now_node.c:218: 동일 수정(공유 구조체라 캠만
     고치면 센스 빌드가 깨짐 — SCD41용 cask 변수형/DHT22 등 레거시 변수형 둘 다 수정)
7. 빌드 검증 — Cntl/CAM/Sens(현재 설정된 변수형인 esp_now_node_cask.c) 전부 정상 빌드
   확인. Sens의 레거시 변수형(esp_now_node.c, DHT22/SHT45/SHT40용)은 지금 빌드 설정에
   안 들어 있어 컴파일러로 직접 검증은 못 함 — 같은 패턴의 기계적 수정이라 안전할 것으로
   판단하나 별도 확인 필요.
8. 실기 검증 — 콘(COM19, assets.bin 제외 앱 파티션만 플래시해서 설정 안 날림)/캠(COM17)
   재플래시 후 브(COM18) 로그로 확인: PAIR_REQUEST가 이번 세션 최초로 성공
   (RL(S/.../OK) PAIR_REQ, 이어서 실제 PAIR_ACK 수신 확인). 세션 내내 안 되던 페어링이
   이 수정으로 됨.
9. 페어링 직후 새 현상 발견(원인 미조사, 범위 밖) — 캠이 그동안 쌓인 사진을 한꺼번에
   전송 시도하면서 브의 ESP-NOW 수신 큐(깊이 8)가 반복 오버플로우("수신 큐 가득참 —
   드롭"), LVGL 락 획득 실패 반복, CAN 릴레이 FC 타임아웃 1회(Relay fail: ERR-TIMEOUT)
   발생. 이건 PAIR 단계가 아니라 다음 단계(캐스크/사진전송)의 문제.
