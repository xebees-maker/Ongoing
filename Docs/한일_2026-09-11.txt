4. 콘 SD카드 신뢰성 재설계 — 태스크 격리 제거 + Fail 회로차단기
   - 이전 세션에 "SD가 몇 초씩 멈춘다"는 증상을 "행(hang)"으로 오판해 만든 잘못된 태스크
     격리 아키텍처(전용 워커태스크+뮤텍스 2개+세마포어)를 전부 제거. 사용자 주도 소크라틱
     대화로 fail/행/죽음 3분류를 재정립("제일 바보같은 코딩은 fail인 결과를 무시하다가
     프로그램을 먹통만들거나 죽이는 거") — 실제 증상은 fail(유한시간 내 리턴하는 SD 명령
     타임아웃)이 반복 누적된 것뿐이었음, 행이 아니었음.
   - `stats_store.c`에 `stats_store_had_io_error()` 신설 — fopen 등 진짜 I/O 실패와
     "그냥 데이터 없음"을 구분해서, 통계탭 조회 시 첫 실패에서 그 틱 전체를 즉시 중단하는
     회로차단기 구현.
   - `sd_storage.c`에 `sd_storage_reconnect()`(재마운트)/`sd_storage_format()`(포맷)/
     `sd_storage_is_mounted()` 신설. 주화면 SD 상태 라벨 + 상태아이콘(기존 에러/워닝
     3단계 아이콘 재사용, 새로 안 만듦)에 조치 UI 연결.
   - 쓰기경로(`esp_now_hub.c`)도 채널별로 따로 fopen하던 걸 `stats_store_append_batch()`
     하나로 모아 한 번만 열게 통합(크래시 시 파일깨짐 위험구간도 축소), 쓰기실패도
     cross-task 플래그로 안전하게 LVGL쪽에 전달해 회로차단기에 편입.
   - 미마운트 상태에서도 fopen을 무조건 시도하던 버그 발견/수정(사용자 지적: "마운트가
     안됬는데 왜 리드라이트를 시도했지?") — 미마운트면 시도 자체를 스킵하도록 게이트 추가,
     5008(마운트실패)/5009(I/O실패)가 동시에 뜨던 모순도 이걸로 해소.

   - "팝업 닫기" 컨벤션 확립(프로젝트 전반 적용 예정, 메모리 기록): 콘텐츠 안에 항목별
     실행버튼이 있는 팝업 → 우측상단 X로만 닫음. 팝업 자체가 하나의 값/결정이고 버튼이
     그걸 실행하는 팝업 → 하단 버튼(확인/취소 등)으로만 닫음. 에러/워닝 팝업은 전자.
   - 목록의 각 행마다 자기 조치버튼: 일반 에러/워닝은 "지우기"(개별 이력 삭제,
     `ui_log_clear_one_error()`/`ui_log_clear_one_warn()` 신규) — 기존 "워닝만 전체삭제,
     에러는 영구" 비대칭 정책 폐기, 전부 개별 해제로 통일.
   - SD 관련 행(5008/5009)은 처음엔 코드별 전용버튼(재연결/포맷)이었다가, "단순 재시도만
     으론 근본원인 있으면 무한루프"라는 사용자 지적으로 공용 "해결(Resolve)" 버튼 하나로
     재통합 — 누르면 재마운트/포맷 둘 다 고를 수 있는 선택팝업이 뜸(코드에 따라 조치를
     강제하지 않음).
   - SD는 재연결/포맷 성공 + 실제 검증읽기까지 통과했을 때만 정상으로 되돌아감(API가
     OK를 반환해도 그대로 안 믿음), 실패 시엔 선택팝업이 안 닫히고 그대로 유지되도록
     수정(처음엔 실패해도 팝업이 전부 닫혀서 주화면으로 튕기는 버그가 있었음).
   - 주화면 SD 상태 라벨도 "SD:" 제목으로 통일하고, 상태별 메시지+색상(정상=기본색,
     에러=빨강)을 함수 하나(`set_storage_label_text()`)로 합침 — 처음엔 이 조합을 여러
     곳에 하드코딩해서 제목이 "Storage"/"SD:"로 갈리던 버그가 있었음.

6. **콘 SD "포맷 실패" 근본원인 진단 — 삽질 끝에 실제 코드버그 발견(중요, 반성 포함)**
   - 실기에서 포맷이 계속 "SD format failed"로 실패. 시리얼 실측: `f_mkfs failed (3)`
     (FatFs FR_NOT_READY) → ESP-IDF 소스 추적: `disk_initialize()`가 `sdmmc_get_status()`
     (CMD13)로 먼저 카드 상태를 확인하는데 이게 실패해서 포맷 시도 자체를 안 하고 있었음.
     "재연결을 포맷 직전에 한 번 거치면 카드가 리셋될 것"이라 판단해 1차 수정 적용.
   - 그런데도 포맷은 계속 실패, 게다가 재연결 자체도 `esp_vfs_fat_sdspi_sdcard_init
     failed (0x107)`로 실패 — **이 시점에 "카드가 물리적으로 죽었다, 교체해야 한다"고
     잘못 단정**하고 SD 로우레벨 포맷/복구 도구를 웹서치까지 함(전부 무관한 결과).
   - 사용자가 직접 카드를 새 걸로 교체(콘 켜진 채)했는데도 재연결 실패, 하지만 **리붓하면
     연결됨**을 실측 — 사용자의 지적("코드에 문제가 있다는 거 같은데", "마운트가 안됬는데
     왜 리드라이트를 시도했지?")을 계기로 코드를 다시 읽어 진짜 원인 발견: CS(CH422G
     EXIO4)를 최초 1번 LOW로 내린 뒤 프로젝트 전체에 다시 HIGH로 올리는 코드가 전혀
     없었음 — 재연결해도 CS가 계속 LOW로 고정된 채라, 새로 꽂은 카드가 SPI모드 진입에
     필요한 "CS HIGH 유지 후 LOW로 내려가는 엣지"를 못 받았던 것. 완전 리붓만 되는 이유도
     설명됨(CH422G 자체가 전원과 함께 리셋되며 이 엣지가 자연히 한 번 생김).
   - 수정: `sd_storage_init()`(부팅/재연결 공용)이 이제 CS HIGH → SPI버스 초기화 → 100ms
     대기(전원/신호 안정화, ESP32-S3 커뮤니티에도 보고된 완화책과 결합) → CS LOW → 마운트
     순서로 동작. **최종 확인**: 사용자가 "죽었다"던 카드를 뽑아 다른 PC의 SD리더에
     꽂아보니 완전 정상 읽힘(카드는 처음부터 멀쩡했음), 같은 카드를 콘에 다시 꽂아도 새
     펌웨어에서 잘 읽힘 — 버그 확정 수정.
   - **반성**: 이 과정에서 "물리적 교체 필요"라는 하드웨어 탓을 했다가 완전히 틀렸고(카드는
     항상 정상이었음), 게다가 "빌드+부팅확인 완료"를 실제 기능이 동작하는 것처럼 여러 번
     보고해서 사용자가 몇 시간을 허비함. 사용자 지적: "네가 하드웨어 의심하는 병이 있다는
     걸 까먹었어", "네 버그를 자꾸 네가 할 일 다했다고 하거나, 하드웨어 의심하는 것좀
     안했으면 하는데. 도대체 몇 시간을 날린거야" — 둘 다 메모리에 재발방지 기록함
     (`feedback_no_hardware_blame_cntl_arbiter`, `feedback_dont_declare_done_prematurely`).
