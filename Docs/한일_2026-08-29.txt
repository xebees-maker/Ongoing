2. "찾기" 팝업 — 스캔→선택→비번입력→접속 전체 구현
   - 초기 설계에서 "재시작 필요"로 가정했다가 사용자가 직접 정정: "AP-STA는 재시작/
     STA로서 AP를 찾고 선택하고 접속하는 일련의 과정은 재시작 안함. 맞아?" 내가 ESP-NOW
     복구를 근거로 재시작이 필요하다고 반박했으나, 사용자가 `esp_now_channelsync`
     컴포넌트(실제 공유기 CSA 채널전환도 이미 이 메커니즘으로 처리됨을 확인시킴)를
     근거로 논파 — 재시작 없이 실시간 접속 시도로 재설계.
   - UI 반복 개선: 팝업 크기(화면 2/3), 비번 보기/숨기기를 눈 아이콘으로(요즘 유행
     스타일, 입력창 우측 안쪽), SSID+비번 한 줄 배치, 별도 상태 레이블 제거하고 버튼
     캡션+토스트로 대체, "다시 찾기"를 "닫기" 왼쪽에 배치.
   - 이전에 접속했던 SSID를 다시 선택하면 비번 자동 채움 → "여러 개 비번 저장
     가능하지?" 질문에서 다중 저장 구조로 확장(8슬롯 LRU, PSRAM).

3. 크래시 버그 1 — 연결 성공 직후 리셋 (스택오버플로우)
   - 재현: 옳은 비번으로 바로 연결 성공 시 화면이 깨지며 리셋.
   - 첫 캡처 시도는 print()가 cp1252 콘솔에서 한글 UnicodeEncodeError로 죽어서 캡처
     내용을 통째로 잃어버림 — 파일에 바이트로 쓰는 방식으로 스크립트 수정 후 재현
     요청, 이번엔 성공적으로 캡처.
   - 로그: "***ERROR*** A stack overflow in task sys_evt has been detected." 원인: WiFi
     이벤트 콜백(2304바이트 스택) 안에서 `device_config_save()`(784바이트+파일I/O) +
     LVGL 팝업 삭제 + 토스트 생성을 전부 동기 실행. `lv_async_call()`로 LVGL 자신의
     태스크로 미루고, `CONFIG_ESP_SYSTEM_EVENT_TASK_STACK_SIZE` 2304→6144로 확대.

4. 크래시 버그 2(라고 생각했던 것) — 틀린 비번 후 재시도 반복 실패/지연

     "실패 후 원래 네트워크로 되돌리기" 재연결이 아직 안 끝난 채 새 시도가 겹침.
   - DISCONNECTING→CONNECTING 2단계 상태머신 도입(새 시도는 항상 먼저 disconnect →
     그 확인 이벤트를 받은 뒤에야 진짜 접속 시작), 타임아웃 15초→25초.

5. 재시험에서 새 증상 발견 — "첫 시도 25초 대기 후 무반응 실패, 재시도는 즉시 실패"
   - 사용자가 정확한 관찰로 패턴을 좁힘: "장치 부팅 후 첫 시도 때에는 25초동안
     대기하다가 실패야. 그런데, 리셋 없이 이 창에서 다시 연결 시도하면 즉시
     연결실패야." → "그러니까 지금의 문제도 2개야" → "하나는 연결 자체가 실패하는것.
     또하나는 재시도 때 (겉으로 보기에) 시도 없이 패일 처리하는 것"
   - 원인1(25초 무반응): STA가 이미 idle이면 `esp_wifi_disconnect()`가 끊을 대상이
     없어 이벤트를 아예 안 만들어냄 → DISCONNECTING 단계에서 영원히 대기하다 타임아웃.
   - 원인2(즉시 실패): CONNECTING 단계의 첫 disconnect를 곧장 실패로 판정하던 로직 —
     실제 WiFi 인증은 흔히 재시도를 거쳐야 성공(성공 로그에도 "Association refused
     temporarily... comeback time" 확인).
   - 사용자의 강한 지적: "이런 식으로 시간 늘리고 타이머 거는 거 아주 안 좋은 버릇이야.
     논리적으로 합당한 시간을 걸거나 타이머 없이 처리되도록 하는 게 맞아." + "이번
     뿐이 아닌 걸 얘기하는데 넌 또 국지적으로 답을 하는구나" — 타이머로 증상을 덮는
     습관이 이 버그 하나가 아니라 전반적 패턴이라는 지적.
   - 수정: `esp_wifi_sta_get_ap_info()`(완전연결 여부만 앎) 대신, `esp_wifi_connect()`
     호출 시 true, 진짜 STA_DISCONNECTED 수신 시에만 false로 스스로 추적하는
     `s_sta_conn_in_flight` 플래그 신설. CONNECTING 단계 disconnect는 실패 판정 없이
     그냥 재시도, 기존 25초 타임아웃 하나로만 최종 판정(새 타이머 추가 아님).

   - 사용자가 정확히 재현 시퀀스를 서술: "설정-네트워크에 iptime 있음->찾기 팝업에

     설정-네트우크에 찾기로 바뀜->찾기 팝업에 연결된 네트워크 없음 -> 이후 계속 같은
     상태(IP time 안나옴)"
   - 원인: `trigger_wifi_scan()`이 스캔을 위해 팝업 열자마자 무조건
     `esp_wifi_disconnect()`를 걸고 있었음. "이미 같은 AP 선택시 재접속 생략" 단축
     경로가 이 끊긴 상태를 재연결시켜주지 않아서, 실제로 WiFi가 끊긴 채 방치됨(표시
     버그가 아니라 진짜 단선). 리스트의 "[연결됨]" 체크도 실시간 IP 유무로 판단해서
     스캔 중엔 항상 비어있어 체크가 안 뜸.
   - 사용자의 아키텍처 교정: "찾기 팝업을 열때 먼저 걸지마. 비번창에서 연결 누를 때
     esp_wifi... 을 걸어야 되." — 이미 `esp_now_hub_test_sta_connect()`가 접속 시도
     시점에 자체적으로 disconnect-then-connect를 처리하므로, `trigger_wifi_scan()`의
     선제적 disconnect 제거만으로 해결. 3개 표시버그 전부 이 하나의 원인에서 파생된
     것으로 확인("그 함수 호출 위치 잘못 잡아서 여태 문제였군").

9. 간헐적 크래시는 미해결로 보류

     경합(race) 창을 피해가는 듯, 재현이 안 됨.
   - 사용자 관찰: "아까 크래시 날 때는, 검색도 잘 안됬었고 다시 찾기도 제대로 안됬었어.
     뭔가 불안정했던 것 같아." — 8번 수정 전의 불안정한 상태(선제 disconnect 버그)와
     연관 가능성 있으나 확정 못함.
   - 결정: "간헐적 크래시 문제는 두고, 나중에 덤프떠서 잡는 방식으로 잡기로 하고, 일단
     마무리 하자." — 다음 세션에 ESP-IDF 코어덤프-to-flash 파티션 설정 예정.
