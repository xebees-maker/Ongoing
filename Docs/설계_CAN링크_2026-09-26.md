# 콘–브–노드 통신 설계 (CAN 링크 + 무선 구간) — 2026-09-26

사용자 설계를 대화로 확정한 내용. 구현은 이 문서를 기준으로 한다.
배경: 캠 2대 연결 시 페어링/CASK가 무너짐 — 원인은 브가 콘의 RELIABLE_SEND를 태스크 하나에서
순차·블로킹 처리(요청당 최대 timeout×시도)해서, 뒤에 온 WAKE_HELLO_ACK·다른 캠 요청이 모두 밀린
head-of-line blocking. CAN CONTROL 채널은 정의만 있고 콘/브 어디에도 구현 안 됨(전부 DATA 한 줄).
비트레이트를 500k로 낮춰도 타임아웃·무응답 수는 그대로(버스 에러만 1/4) → 비트레이트 문제 아님.

## 0. 계층 역할

- **캠/센스 ↔ 브 (무선, ESP-NOW)**: 무선 구간 신뢰성은 브에서 끝낸다(네트워크 하부 계층의 일 —
  "판단은 콘 한 곳" 원칙에 안 걸림).
  - 콘→노드 reliable 요청: 브가 대행(재시도·응답 대조), 결과만 CAN으로 콘에.
  - SR(사진 전송): 브가 끝점. META/WINDOW_STATUS/DONE과 그 ACK를 브가 처리.
- **브 ↔ 콘 (CAN)**: 애플리케이션 메시지와 순서 맞춘 사진 데이터만. 청크 누락 확인·재전송 같은
  전송 제어는 CAN에 안 실림.
- **앱 ACK는 콘이 만든다**: 앱이 상태를 알아야 하는 요청(WAKE_HELLO, CAM_CONFIG, CAPTURE_STATUS 등)의
  ACK는 콘이 생성, 브는 전달만(에러 복구가 아니라 상위 계층의 상태이므로).

## 1. 메시지 분류

| 분류 | 메시지 | CAN 경로 |
|---|---|---|
| SR(사진) | 캠↔브: PHOTO_META/META_ACK, PHOTO_CHUNK, WINDOW_STATUS_REQUEST/ACK, PHOTO_DONE/DONE_ACK (브가 처리) · 브→콘: META 정보, 순서 맞춘 청크, 완료 통지 | Data |
| reliable | PAIR_REQUEST/ACK, UNPAIR/ACK, WAKE_HELLO(_SENS)/ACK, CAM_CONFIG_SET·SENS_CONFIG_SET/ACK, CASK_WORK_NONE/ACK, PHOTO_REQUEST(CAPTURE_NOW), CAPTURE_STATUS/ACK, SLEEP_NOW/ACK | Control |
| fire-and-forget 유지 | ADVERTISE(브로드캐스트), ADVERTISE_ACK | Control |

- CAPTURE_STATUS(RECEIVED): 지금은 캠 recv_cb에서 fire-and-forget → **태스크로 옮겨 reliable로 변경**.
- BENCH_START / BENCH_BLAST: **삭제**.
- 캠 SD 제거로 죽은 메시지(PHOTO_LIST_*, PHOTO_DELETE_*, DELETE_ALL_*, LIST_ENTRY, CHUNK_NACK)와 콘
  쪽 호출처 없는 함수(esp_now_photo.c의 목록/가져오기/삭제/전체삭제)는 정리.

## 2. CAN 채널과 우선순위

| 경로 | 콘→브 | 브→콘 |
|---|---|---|
| Control | 0x100 | 0x101 |
| Data | 0x200 | 0x201 |

- 낮은 ID가 중재에서 이김 → Control 프레임이 Data 프레임 사이에 먼저 끼어듦.
- FC는 받는 쪽이 자기 ID로 보냄(현행 유지) → Data의 FC가 Control 세션을 방해 안 함.
- ID(방향·경로)마다 ISO-TP 세션 1개(송신 뮤텍스, 현행 유지). 받는 쪽은 ID별 조립 버퍼·큐 분리.
- **분류 기준은 Common의 함수 하나**(예: `can_bridge_path_for_msg_type()`, ESP-NOW msg_type 기준).
  브(무선→CAN)와 콘(콘→CAN)이 둘 다 이 함수만 씀.

## 3. 처리 태스크

우선순위: Control 17, Data(SR) 15 (기존 체계 통신17/SR15/파일10/UI6). 코어: 콘 CAN=1 / 브 CAN=1, ESP-NOW=0.

**브**
| 태스크 | 코어 | 우선순위 | 역할 |
|---|---|---|---|
| can_rx | 1 | 17 | 프레임 수신, ID로 Control/Data 조립기에 분배 |
| ctrl_consume | 1 | 17 | 콘 Control 메시지: RELAY는 즉시 무선 송신, RELIABLE_SEND는 비동기 요청만 걸고 다음으로(블로킹 없음) |
| data_consume | 1 | 15 | 콘 Data 메시지(있으면) 처리 |
| ctrl_relay | 0 | 17 | 무선→CAN Control 전달 + RELIABLE_RESULT 송신(결과 큐) |
| data_relay | 0 | 15 | SR: 순서 맞춘 청크/META/완료를 CAN Data로 콘에 |
| reliable 서비스 | 0 | 17 | esp_now_reliable 내부(4절) |

- recv_cb는 msg_type으로 분류해 **큐 두 개** 중 하나에 넣음(지금은 큐 1 + 릴레이 1이라 청크 하나
  보내는 동안 WAKE_HELLO가 뒤에서 기다림).

**콘**
| 태스크 | 코어 | 우선순위 | 역할 |
|---|---|---|---|
| can_rx | 1 | 17 | ID로 Control(0x101)/Data(0x201) 분배 |
| ctrl_consume | 1 | 17 | node_hub로(WAKE_HELLO, ACK, 대행 결과) |
| data_consume | 1 | 15 | photo_rx로(순서 맞춘 청크 이어 붙이기, CRC 누적) |
| node_request 디스패처/노드별 작업 | 1 | 17 | 노드별 순서 보장, RELIABLE_SEND 후 결과 대기(현행 esp_now_tx 구조 유지) |

**이름 변경(구현과 함께)** — 콘에는 ESP-NOW 무선이 없음(원래 PC에서 지시했으나 미반영):
- `esp_now_hub` → `node_hub`, `esp_now_photo` → `photo_rx`, `esp_now_tx` → `node_request`
- node_hub 안의 Wi-Fi STA 함수들(get_own_ip_str, test_sta_connect, sta 재연결 등) → `wifi_sta.c/.h`, `wifi_sta_*`
- `esp_now_link.h`(노드와 공유하는 무선 프로토콜 정의)는 그대로.
- 태스크/로그 태그 이름도 같이.

## 4. 블로킹 규칙

1. 수신 처리 태스크(consume/relay)는 상대 응답을 기다리지 않는다 — 분류·전달만.
2. 콜백(recv_cb, send_cb, CAN ISR)은 블로킹 금지 — 복사+알림만.
3. Control과 Data는 큐·태스크·ISO-TP 세션을 공유하지 않는다.
4. 노드 하나의 지연이 다른 노드를 막지 않는다 — 노드당 reliable 요청은 한 번에 1개(콘 node_request가
   보장), 서로 다른 노드는 동시에 진행.
5. 모든 기다림에는 상한이 있다(5절).

**esp_now_reliable 비동기화 (브의 RELIABLE_SEND 대행용)**
- 노드별 슬롯 표(노드 수만큼, 예: 8): MAC, 요청 복사본(PSRAM), 받을 응답 종류, 1회 대기, 남은 시도,
  타이머, 완료 콜백+인자, 응답 버퍼. 노드당 슬롯 1개 — 진행 중인 노드에 새 요청은 즉시 거절
  (ESP_ERR_INVALID_STATE, 버그로 로그).
- `esp_now_reliable_request_async(peer, req, len, accept_types, count, timeout_ms, max_attempts, cb, ctx)`
  — 슬롯 잡고 복사 후 즉시 반환, 결과는 `cb(ctx, result, reply, reply_len)`.
- 내부 서비스 태스크 1개가 알림으로만 깨어나 송신/재전송 처리: 새 요청, 슬롯 타이머 만료, 송신 큐
  자리 생김(send_cb → `esp_now_reliable_on_send_done()`). NO_MEM이면 슬롯을 "송신 대기"로 표시.
- 응답 대조는 `esp_now_reliable_on_recv()`(현행)가 보낸 MAC+msg_type으로 슬롯을 찾아 완료.
- 콜백은 recv_cb/서비스 태스크 안에서 불림 → 블로킹 금지(결과 큐에 넣고 알림만).
- 슬롯 표는 짧은 잠금으로 보호(잠금 안에서는 복사·상태 변경만).
- 기존 `esp_now_reliable_request()`(동기)는 비동기 + 세마포어 대기 포장으로 유지 → 캠/센스 코드 그대로.
- 브 흐름: ctrl_consume이 request_async만 걸고 넘어감 → 완료 콜백이 결과 큐에 → ctrl_relay가
  RELIABLE_RESULT를 CAN Control로 콘에.

**SR 수신 (브, 캠별 상태 — 이 API 안 씀)**
- 캠이 요청(META/WINDOW_STATUS/DONE)하고 브가 즉시 답하므로 브 쪽에 기다림 없음.
- 브는 **순서만 맞춘다**: 빠진 번호가 있으면 그 뒤 청크를 잠깐 보관, 빈자리가 채워지면 이어지는
  청크를 순서대로 콘에 전달. 보관량은 최대 윈도우 1개(16청크×1200B≈19KB)/캠, 사진 전체는 안 들고 있음.
- 콘은 받는 대로 이어 붙이고(SD에 순차 쓰기) CRC 누적, 완료 통지 후 CRC 검증.
- 흐름 제어: 무선이 CAN보다 빠르면 브가 큐가 일정량 아래로 빠질 때까지 WINDOW_STATUS 응답을 늦춤
  → 캠 송신 속도가 CAN에 맞춰짐(캠 타임아웃은 5절에서 이 지연 감안).

**4단계 구현 순서(2026-09-26 밤 정리)** — 캠은 바꿀 것 없음(캠의 허브 MAC이 이미 브이므로 SR 상대만 콘→브로 바뀜)
1. **브→콘 SR 스트림 형식** — 완료. `can_bridge_link.h`의 `CAN_DATA_SR_META / SR_CHUNK / SR_DONE`(Data 경로,
   mac=캠) + `can_bridge_sr_meta_t / can_bridge_sr_chunk_hdr_t / can_bridge_sr_done_t`. SR_CHUNK는 항상
   chunk_idx 순서(빠짐·중복 없음). CRC는 캠과 같은 `esp_rom_crc32_le`로 청크마다 누적(시작값 0).
2. **콘 수신(photo_rx)**: SR_META에서 SD 임시파일(.tmp) 열기 → SR_CHUNK를 받는 대로 순차 쓰기 + CRC 누적 →
   SR_DONE(COMPLETE)에서 CRC 비교 후 rename, ABORTED면 임시파일 삭제. 사진 전체를 PSRAM에 안 모음.
   화면 표시용 캐시(최근 사진)는 파일에서 읽거나 기존 캐시 방식 유지 — 구현 때 결정.
3. **브 SR 엔진(캠별 상태)**: file_id·총 청크·다음 기대 번호·보관 버퍼(최대 윈도우 1개, PSRAM).
   META→META_ACK + SR_META, CHUNK→순서가 맞으면 즉시 SR_CHUNK(이어지는 보관분도), 아니면 보관,
   WINDOW_STATUS_REQUEST→누락 목록 ACK(Data 송신 큐가 임계 이상이면 응답을 늦춰 흐름 제어),
   DONE→DONE_ACK + SR_DONE. 캠 무응답·새 META로 끊기면 SR_DONE(ABORTED).
4. **전환**: 브가 SR 7종을 콘으로 RELAY하지 않음. 콘의 기존 SR 수신(윈도·누락 목록·DONE_ACK 생성) 코드 삭제.
5. 실기 확인(캠 2대, OV5640 1MB 포함): 누락 0, CRC 일치, 브 보관 버퍼 최고치, CAN Data 큐 최고치.

## 5. 타임아웃 (구현 후 측정으로 숫자 확정)

- 1회 대기 = 왕복 경로 구간 합(무선 송신, 브 큐, CAN, 콘 처리, 반환) + 여유. 재시도 횟수는 유실
  흡수용이지 지연을 때우는 용도가 아님.
- 겹친 대기는 바깥 > 안쪽: 브 대행 전체 = 1회 대기×시도, 콘 CAN 대기 > 브 대행 전체 + CAN 왕복 + 여유.
- 구간별 실측(로그 타임스탬프): 1M/500k × 캠 1대/2대 × 사진 전송 중/아님. 최악값+여유를 표로,
  코드 상수는 한 곳에서 관리. 현재 값(캠 200ms, 대행 800ms, 콘 +2초, SR 400ms×3)은 근거 없음.

## 6. 오류 처리

- 원칙: 브 재부팅/CAN 끊김은 복구하지 않고 콘/브/캠/센스를 최초 상태로(콘에 저장된 것 제외).
- 콘이 죽음 → 사용자가 리셋. 캠이 죽음 → 연결 끊기고 끝.
- 브가 죽음 → 콘이 알아야 함:
  - 브 재부팅: 브가 부팅 시 Control로 "부팅했음" 1회 통지 → 콘이 노드 상태 전부 초기화. 캠은
    WAKE_HELLO 실패 → 재광고 → 재페어링으로 스스로 복귀.
  - 브 멈춤: 콘 화면에 경고. 복구는 (가) 콘이 주기적 Control PING, PONG 끊기면 RESET 전송
    (나) 브 자체 워치독 재부팅(→ 재부팅 경로). 둘 다 안 되면 사용자가 전원 리셋(경고 문구로 안내).
- 버스 에러: 원인은 못 밝힘, 전파 간섭은 아님(보드 소프트웨어 동작에 따라 달라짐 — 한일 문서 참고).
  `fail_retry_cnt`: ESP32-S3(HAL v1)에서는 -1이 아니면 single-shot(재전송 없음)이라 예전 3은 "에러 프레임
  즉시 폐기"였음 → 2026-09-26 -1(하드웨어 재전송)로 변경. 버스 오프 때 드라이버가 버리는 송신 중 프레임은
  can_bridge_tx_pool_on_bus_off_isr()로 정리하고 즉시 복구.
- **미정**: 재전송 이후 운용에서 bus_off 반복(캠 켠 상태) — 원인 확인. 무한 재시도 방어(상대 노드가 없을 때
  같은 프레임 영원히 재전송, 버스 오프 반복 시 백오프/앱 알림). ISO-TP 세션 실패(FC 타임아웃, CF 순번 어긋남)를
  어느 선부터 "끊김"으로 볼지.

## 7. 비트레이트

- 1M 사용 중(500k 실험은 되돌림 — 500k가 에러율이 더 높았음).
