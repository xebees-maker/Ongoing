### 1. LOLIN C3 Pico 단일-센서 헤드리스 노드 패밀리 (메인 작업)

기존 Sens는 Waveshare ESP32-C6-Touch-LCD-1.47 한 대에 DHT22+SCD41을 같이 붙이고 LVGL 화면까지
갖춘 단일 앱이었음. 앞으로는 센서를 하나씩 따로 붙인 독립 물리 장치(SCD41/DHT22/SHT45/SHT40,
추후 추가 예정)로 가고, 하드웨어는 화면 없는 LOLIN C3 Pico(ESP32-C3)로 옮기기로 함. 상세 설계
결정/전체 변경 내역은 글로벌 메모리 `project_sens_headless_sensor_family` 참고. 요약:

- **프로토콜**: `Common/components/esp_now_link/include/esp_now_link.h`의 `esp_now_sensor_data_t`를
  `dht_temp`/`co2` 같은 고정 필드 대신 `{sensor_kind, chan_count, chan_type[], chan_ok[], chan_val[]}`
  일반 채널 배열로 교체 (breaking change, `ESP_NOW_LINK_VERSION`을 2로 올림). 새 센서가 추가돼도
  프로토콜/Cntl을 다시 안 고쳐도 되는 게 목표.
- **Sens 빌드 구조**: 프로젝트 하나 유지, `idf.py menuconfig` → `Sens Sensor Node` 메뉴에서
  `SENS_BUILD_TARGET`(레거시 LCD 콤보 vs 헤드리스, 기본 헤드리스) + `SENS_SENSOR_TYPE`(SCD41/DHT22/
  SHT45/SHT40) 선택. `Sens/main/CMakeLists.txt`는 `SRCS`만 조건부로 가르고 `REQUIRES`는 두 빌드
  타깃의 합집합으로 고정 — 이유는 아래 "발견한 것" 참고.
- 신규 컴포넌트: `Common/components/status_led`(LED 패턴 드라이버), `Common/components/sensor_sht4x`
  (SHT45/SHT40 공용 드라이버), `Sens/components/bsp_c3_pico`(헤드리스 BSP — **GPIO는 전부 TODO
  플레이스홀더**, 실물 핀아웃 확인 전 배선 금지).
- 신규 앱: `Sens/main/sensor_node.c` (LVGL 없는 헤드리스 버전, Kconfig로 고른 센서 하나만 컴파일).
- `esp_now_node.c` 재작성: Green LED 상태머신 추가(아래 3번), 앱이 채널 배열을 push하는 모델로
  전환(`esp_now_node_set_readings()`) — `sensor-c6.h`(구 pull 모델) 삭제.
- `Sens/main/wifi_dashboard.c`, `Cntl/main/web_dashboard.c`, `Cntl/main/ui_node_tabs.c`,
  `Cntl/main/esp_now_hub.h/.c`도 전부 dht/scd 하드코딩 대신 채널 타입별 일반 렌더링/집계로 전환.
- `Common/components/history_log`: metric enum을 `HISTORY_METRIC_DHT_TEMP` 같은 이름 있는 값 대신
  `CH0~CH4`+`BATT_PCT` 슬롯으로 축소, `history_log_set_scale()` 추가(CO2처럼 값 범위가 큰 지표는
  int16 NVS 링버퍼 오버플로 방지를 위해 배율을 1.0으로 낮춰야 함).

**발견한 것 — ESP-IDF `REQUIRES` 조건부 버그:** `idf_component_register(REQUIRES ...)`를
`if(CONFIG_X)`로 가르면 안 됨 — ESP-IDF가 sdkconfig를 다 읽기 전 "컴포넌트 요구사항 조기 확장"
단계에서 `REQUIRES`를 한 번 평가하는데, 그 시점엔 Kconfig 값이 없어서 항상 `else()` 쪽으로
평가돼버림(실기 확인됨). `SRCS`는 이 문제가 없음(실제 빌드 단계에서 재평가됨). 그래서 `SRCS`만
조건부로 가르고 `REQUIRES`는 합집합으로 고정하는 패턴을 씀. 상세는 `reference_espidf_manual_build_env`
메모리 참고.

**빌드 검증**: 헤드리스 SCD41/DHT22/SHT45(SHT40은 SHT45와 코드 동일해서 생략), 레거시 LCD 콤보,
Cntl — 5개 구성 전부 `idf.py` 없이 직접 ninja/cmake로 클린 빌드 확인(경고 0개). `idf.py` 자체는 이
환경에서 안 됨(자체적으로 잘못된 python venv 경로를 찾음) — 수동 빌드 절차는
`reference_espidf_manual_build_env` 메모리에 정리해둠.

### 2. SCD41 stale 복구 버그 발견 + 수정, 그리고 실제 원인은 배선 문제였음

- 사용자가 "SCD41이 stale에서 복구가 안 됨(Waveshare S3 1.47)"이라고 보고.
- 코드 리뷰로 실제 버그 발견: `Common/components/sensor_scd41/scd41.c`의 `data_ready()`와
  `scd41_read()` 양쪽 CRC 불일치 분기가 `note_failure()`/`check_stale()` 어느 워치독도 안 불렀음 —
  "통신은 되는데 데이터가 깨지는" 실패 모드가 두 워치독을 다 새어나감. 양쪽에 `note_failure()` 호출
  추가해서 고침, 빌드 확인.
- 이후 증상을 더 자세히 들어보니(CO2는 항상 stale/0, 온습도는 복구되지만 곧 다시 stale로) 이건
  CRC 버그로 설명이 안 되는 패턴이라고 분석해줬는데(재초기화 직후 한 번만 읽히고 다시 죽는 반복
  패턴 — 하드웨어 결함 의심), **사용자가 직접 확인한 결과 접촉불량(배선 문제)이었고 현재는 정상
  동작함.** 하드웨어 결함 우려는 접어도 됨. `project_sens_scd41_recovery` 메모리에 전체 경위 기록.

### 3. 상태 LED 2개 설계 (Green=ESP-NOW, Blue=배터리/센서) — 여러 번 반복 확정

최종 확정된 표(전부 배선 전에 미리 값 지정, `project_sens_headless_sensor_family` 메모리에 상세):

**Green (ESP-NOW 링크 상태):**
| 상태 | 패턴 |
|---|---|
| Paired | 50ms on / 2.95s off (heartbeat) |
| Advertising (30초 이내) | 0.1s on/off (빠른 깜박임) |
| Failed (페어링 끊김 또는 30초+ 미페어링) | 1s on/off (느린 깜박임), advertising은 백그라운드 계속 |

**Blue (배터리 잔량 / 센서 이상):**
| 상태 | 패턴 |
|---|---|
| 배터리 60~100% | 50ms on / 2.95s off (heartbeat) |
| 배터리 20~60% | 50ms on / 1s off (heartbeat-fast) |
| 배터리 0~20% | 50ms on / 300ms off (heartbeat-urgent) |
| 센서 이상(stale) | 0.1s on/off ×3 + 0.5s 쉼 반복(burst), 배터리 표시 임시 override |

- 리셋 버튼 없음 — 링크 끊김/장시간 미페어링 둘 다 자동 무한 재시도. BOOT 핀은 하우징 밖으로 안 뺌.
- 처음엔 Blue에 3번째 LED(Red, 센서 이상용)를 추가할지 물었다가, 기존 2개로 커버하는 쪽으로 결정.
- "Paired/배터리 60~100%"처럼 가장 오래 유지되는 정상 상태가 원래 "계속 켜짐"이었는데, 사용자가
  전력 낭비를 지적해서 전부 저듀티 heartbeat 계열로 교체(원래 설계 문서에 있던 "계속 켜짐"은 이제
  안 씀 — Green/Blue 둘 다 heartbeat 계열이 기본, "계속 켜짐" LED_PATTERN_ON은 컴포넌트에 남아있지만
  Sens에서는 안 씀).
- `Common/components/status_led`에 `LED_PATTERN_HEARTBEAT`/`HEARTBEAT_FAST`/`HEARTBEAT_URGENT`/
  `BURST_TRIPLE` 4개 패턴 추가. 공통 `led_phase_seq_t`(ms[]/level[]/count) + `esp_timer_start_once`
  자체 재무장 체인으로 구현(고정 주기 토글로는 표현 안 되는 위상별 다른 지속시간 패턴이라).

### 4. 다음 작업 스펙 확정만 해둠 (절전모드) — 구현은 배선 이후로 미룸

- 순서 확정: **하드웨어 배선/동작 확인이 먼저, 절전모드는 그 다음.** 이유: 절전모드는 esp_timer
  주기 콜백을 완전히 다른 구조(light/deep-sleep 웨이크 타이머)로 바꿔야 해서, 검증 안 된 하드웨어
  베이스 위에 얹으면 문제 원인 구분이 안 됨.
- 스펙(사용자 제공, `project_sens_sleep_mode_spec` 메모리에 상세): 인터벌 5초/10초/30초/1분/3분/10분
  (기본 10초, Cntl UI에서 선택 + "길수록 배터리 오래감" 설명 필요, 사람이 읽을 값이라 1초는 제외).
  SCD41은 **single-shot 측정 모드**로 duty-cycle(기존 continuous periodic 모드 대신 — 확정).
  ESP-NOW도 필요하면 껐다 켬. Cntl→노드 설정 전달용 새 프로토콜 메시지 필요(아직 없음, 현재는
  노드→허브 단방향뿐).
- 전력 예산 논의(정확한 수치는 실측 필요): 딥슬립 수 µA, 라이트슬립 ~1mA, WiFi/ESP-NOW 라디오 켜짐
  수십~100mA+. 라디오 워밍업 비용이 짧은 인터벌에서는 실제 송신보다 더 클 수 있음. LED heartbeat도
  절전 구간엔 꺼야 하고 GPIO 풀업 누설 주의. 레귤레이터 정지전류가 딥슬립 지배적 구간에서 병목 될 수
  있음(하드웨어 이슈, 보드 고를 때 체크).
