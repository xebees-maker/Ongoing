> 헤더에 실제 노출된 GPIO는 1,2,3,4,5,6,7,8,9,12,13,16,17,18,19뿐 (보드 실물 사진으로 확인).
> GPIO10/11은 이 보드에 **존재하지 않음** — 다른 보드 핀맵과 혼동하지 말 것.

### ESP32-C6 LP_IO / 스트래핑 주의사항 (S3와 다른 점)

- GPIO0~7은 **LP_IO(저전력) 도메인**. I2C port 1을 쓰면 자동으로 LP_I2C
  컨트롤러로 매핑되고, SDA/SCL이 GPIO6/7로 하드웨어 고정됨(변경 불가).
- GPIO4, 5, 8, 9, 15는 부팅 스트래핑 핀.
- 이번 디버깅에서 GPIO4/7/8을 다 시도해봤지만 핀 자체는 문제가 아니었음
  (아래 DHT22 섹션 참고). 그래도 향후 새 핀을 고를 땐 위 표의 "비고"를
  먼저 확인할 것.

## DHT22 — 핵심 버그 수정 완료 (`C:\Projects\components\sensor_dht22\dht22.c`)

### 증상

GPIO를 4 → 7 → 8로 세 번 바꿔도 매번 동일하게 "응답 신호 단계 0에서
타임아웃 — 센서 응답 자체가 없음". 배선 연속성(멀티미터), 전압(3.3V 안정),
센서 자체(S3 보드에서 동시 정상 동작 확인)는 전부 정상이었음.

### 근본 원인

`dht22_read()`가 호스트 시작 신호를 보내는 동안 인터럽트가 켜진 채로
방치되고 있었음:

```c
/* 수정 전 (문제) */
gpio_set_direction(s_pin, GPIO_MODE_OUTPUT);
gpio_set_level(s_pin, 0);
vTaskDelay(pdMS_TO_TICKS(2));   // 인터럽트 켜진 상태
gpio_set_level(s_pin, 1);
esp_rom_delay_us(30);           // 인터럽트 켜진 상태
gpio_set_direction(s_pin, GPIO_MODE_INPUT);
portDISABLE_INTERRUPTS();       // 너무 늦게 비활성화
```

호스트가 라인을 놓아준 시점부터 `portDISABLE_INTERRUPTS()` 호출까지의
그 짧은 구간에 LVGL 화면 갱신(SPI DMA)/터치 I2C/FreeRTOS tick 인터럽트가
끼어들면, DHT22가 응답을 시작하는 짧은 윈도우(놓아준 후 20~40us)를
통째로 놓쳐버림. **핀과 무관하게 매번 똑같이 재현되는 이유였음.**

같은 코드가 S3(듀얼코어)에서는 멀쩡히 동작했는데, C6는 싱글코어라
LVGL/SPI/터치 인터럽트가 DHT22 코드와 같은 코어에 몰려서 충돌 확률이
훨�르 높았던 것으로 추정(S3도 같은 취약점이 있었지만 운이 좋았을 뿐).

### 수정 후

```c
/* 수정 후 */
portDISABLE_INTERRUPTS();        // 시작 신호 전부터 비활성화
gpio_set_direction(s_pin, GPIO_MODE_OUTPUT);
gpio_set_level(s_pin, 0);
esp_rom_delay_us(2000);          // vTaskDelay 대신 busy-wait
gpio_set_level(s_pin, 1);
esp_rom_delay_us(30);
gpio_set_direction(s_pin, GPIO_MODE_INPUT);
gpio_set_pull_mode(s_pin, GPIO_PULLUP_ONLY);
/* ... 응답 polling ... */
```

`dht22_init()`에도 `gpio_reset_pin()` + INPUT + PULLUP 기본 설정 추가됨
(IOMUX를 GPIO 기능으로 강제 전환, 큰 영향은 없었지만 안전하게 유지).

**공유 컴포넌트라 S3(startup) 프로젝트도 다시 빌드하면 자동으로 같은
수정이 적용됨.** (S3는 굳이 지금 재플래시할 필요 없다고 사용자가 판단함 —
다른 수정을 더 가할 예정이라서.)

### 진단 기법 (재사용 가치 있음)

오실로스코프/로직 아날라이저가 없을 때, GPIO 레벨 변화를 타임스탬프와
함께 배열에 기록해두고 캡처 끝난 후 한꺼번에 로그로 뽑는 "소프트웨어
로직 아날라이저"로 우회 검증함. 핵심은 **응답 구간만 캡처하면 안 되고,
호스트가 보내는 시작 신호부터** 캡처해야 진짜 원인이 드러남 (처음엔
응답 구간만 캡처해서 "10ms 내내 무응답"으로 오인했었음).

## SCD41 — 정상 동작 확인 (`C:\Projects\components\sensor_scd41\scd41.c`)

### 문제 1: I2C 핀

`i2c_new_master_bus` 실패: `SDA pin can only be configured as GPIO#6`.
I2C port 1이 C6에서 LP_I2C로 매핑되어 SDA/SCL이 GPIO6/7로 고정됨.
→ `SCD41_SDA_PIN=GPIO6`, `SCD41_SCL_PIN=GPIO7`로 수정.

### 문제 2: 클럭 소스

핀을 고쳐도 `the clock source does not support lp i2c` 에러. LP_I2C는
`I2C_CLK_SRC_DEFAULT`(=XTAL)를 지원 안 함. ESP-IDF 헤더
(`esp32c6/include/soc/clk_tree_defs.h`)에서 LP_I2C는
`LP_I2C_SCLK_DEFAULT`(=RTC_FAST)를 써야 한다는 걸 확인.

```c
i2c_master_bus_config_t bus_cfg = {
    .clk_source = (i2c_clock_source_t)LP_I2C_SCLK_DEFAULT,  // I2C_CLK_SRC_DEFAULT 아님
    ...
};
```

### 결과

CO2 ~741~751ppm으로 안정적으로 읽힘. `wake_up`(0x36F6) 명령의
`ESP_ERR_INVALID_RESPONSE`는 정상(슬립 센서를 깨우는 용도, NACK이 기대값).

> S3 프로젝트 메모리에 남아있던 "측정 중 NACK → 캐패시터 필요" 가설은
> **이번에 고친 문제와는 다른 증상**(이번 건 버스 초기화 자체가 안 되던
> 클럭 소스 설정 오류). 캐패시터가 필요 없어진 건 아니고, 더 오래
> 돌려봐서 측정 중 NACK이 재발하는지 별도로 확인 필요.
