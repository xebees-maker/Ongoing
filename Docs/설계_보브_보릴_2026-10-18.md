# 설계: 보브(두 번째 브릿지) + 보릴(보일러 릴레이) — 2026-10-18

사용자와 대화로 정한 내용(10-17 밤 ~ 10-18). 구현 전 설계 문서.

## 1. 배경

- 보일러를 켜고 끄는 무선 장치가 필요함. 보일러는 이동식이고 전파가 차폐된 공간에 있음.
- 콘의 무선은 Wi-Fi(AP 접속) 전용 — ESP-NOW는 쓰지 않음(메모리가 가장 큰 이유). ESP-NOW는 CAN으로 붙은 브릿지가 맡음.
- 지금 브릿지(재브)는 외장 안테나가 벽 반대쪽(실내)에 있어서, 콘·AP가 있는 실외 쪽 기기는 못 들음.
- 그래서 같은 기종의 브릿지를 하나 더 붙임(보브). CAN 데이지 체인.

## 2. 이름

| 이름 | 기기 | 위치 |
|---|---|---|
| 콘 | 제어기(Waveshare ESP32-S3-Touch-LCD-4.3B) | 실외, AP 접속 |
| 재브 | 기존 브릿지(Waveshare ESP32-S3-RS485-CAN, 외장 안테나) | 안테나 실내 — 센스·캠 담당 |
| 보브 | 새 브릿지(같은 기종, SMA 없는 기본형) | 안테나 실외(콘·AP와 같은 공간) — 보릴 담당 |
| 보릴 | 보일러 릴레이 장치(XIAO + 외장 안테나 + 3.3V High 트리거 릴레이 모듈, 상시 전원) | 보일러 옆(차폐 공간) |

## 3. 지금 구조의 한계(조사 결과)

- CAN ID 4개 고정(`Common/components/can_bridge_link/include/can_bridge_link.h`): 콘→브·브→콘 × 제어·데이터.
  설계 전제가 "콘-브 2노드뿐". 브릿지 두 대가 같은 ID로 보내면 버스 충돌(같은 ID·다른 내용 → 비트 에러·재전송 반복).
- 콘 쪽 상태가 하나씩(`Cntl/main/can_bridge.c`): ISO-TP 재조립 버퍼, 브 부팅 ID·무응답 표시, PING/PONG, RESET, "브 재부팅 → 노드 초기화" 콜백.
- 노드가 어느 브릿지에 붙었는지 기록하는 곳이 없음. 전달·신뢰 전송은 대상 MAC만 실음(호출부 약 10곳).
- 브릿지는 자기 번호를 알 방법이 없음(파일 시스템 없음 — NVS와 앱 파티션뿐).
- 브릿지 채널: 지금 재브는 기본값 CH1 그대로(`Bridge/main/bridge_esp_now.c` wifi_bringup). `CAN_CTRL_SET_CHANNEL`은 번호만 정의돼 있고 양쪽 모두 구현 없음.

## 4. 결정

### 4.1 브릿지 번호 — 빌드 변형

- 코드는 하나, 번호만 빌드 때 넣음(센스의 `Tools/sens_variant.ps1`과 같은 방식). 재브 = 0, 보브 = 1.
- 구현(10-18): Bridge/main/Kconfig.projbuild `CONFIG_BRIDGE_INDEX`(기본 0), 보브는 `Tools/bridge_variant.ps1 1`(빌드 폴더 C:\Projectsuild_bridgeridge_1, PowerShell에서 실행 — Git Bash에선 IDF가 MSys 거부). 화면·로그에는 번호+1("Bridge 1" = 재브, "Bridge 2" = 보브).

### 4.2 CAN ID — 번호마다 4개

| | 콘→브 제어 | 브→콘 제어 | 콘→브 데이터 | 브→콘 데이터 |
|---|---|---|---|---|
| 재브(0) | 0x100 | 0x101 | 0x200 | 0x201 |
| 보브(1) | 0x110 | 0x111 | 0x210 | 0x211 |

- 재브는 지금 ID 그대로(번호만 받으면 지금과 똑같이 동작). 제어가 데이터보다 우선(낮은 ID)인 원칙 유지.
- 콘은 브릿지별로 재조립 버퍼·송신 문맥·PING/PONG·부팅 ID·무응답 표시를 따로 가짐. 브릿지별 경고·화면 표시도 따로.

### 4.3 채널 — B안(범위 제한 없음 + 기기 종류로 브릿지 구분)

- 콘은 AP 채널을 따름(Wi-Fi).
- 보브 안테나는 AP·콘과 같은 실외 공간 → **AP와 멀어야 하는 쪽은 보브**. 재브는 실내(벽 너머)라 AP와 겹쳐도 됨(사용자).
- 채널 계산은 콘이 함(AP 채널을 아니까): 보브 = 1~13 중 AP에서 가장 먼 채널, 재브 = 보브에서 가장 먼 채널(AP와 겹쳐도 됨).
  예: AP 10 → 보브 1~3, 재브 11~13. AP 1 → 보브 11~13, 재브 1~3. 콘이 `CAN_CTRL_SET_CHANNEL`로 보냄(구현 필요).
- 기기는 지금처럼 1~13을 훑으며 광고(ADVERTISE). 어느 브릿지로 붙을지는 **콘이 기기 종류로 정함**:
  센스·캠의 광고는 재브를 통해서만 응답(ADVERTISE_ACK), 보릴의 광고는 보브를 통해서만 응답. 다른 브릿지가 들은 광고는 무시.
  기기는 응답을 보낸 브릿지의 MAC·채널에 고정되므로, 그 뒤엔 그 브릿지로만 통신함. 실내 기기가 약한 신호로 보브에 붙는 일은 없음.
- 센스·캠 펌웨어는 바꾸지 않아도 됨.
- 기기 종류 판단: 광고(`esp_now_advertise_t`)의 name — 구체 방법은 구현 때 확인.

### 4.4 AP가 채널을 바꿀 때

- 운영 환경에선 AP 채널이 고정이 아닐 수 있음(사용자). 예전에 공유기가 스스로 6 → 11로 바꾼 것을 관측함.
- 바로 따라가지 않음: 새 AP 채널이 보브 채널과 겹치고(5칸 미만) 그 상태가 일정 시간(제안 10분) 계속될 때만 다시 계산해서 옮김.
- 옮기면 그 브릿지의 기기들은 채널을 잃고 다시 훑어서 찾음.

### 4.5 보릴

- 기기 종류 하나 추가(CASK 위에서): 켜기·끄기 명령(콘 → 보릴, 신뢰 전송), 릴레이 상태 보고(보릴 → 콘).
- **통신이 끊기면**: 마지막 상태를 유지하다가 일정 시간 뒤 끔(사용자).
  - 그 시간은 콘 설정에서 고름: **기본 10분**, 선택 10분 / 30분 / 1시간(사용자 — 통신이 다시 될 수 있으니 길게 할 필요 없음).
  - 끊긴 동안 보릴이 혼자 판단해야 하므로, 값은 콘이 보릴에 보내고 보릴이 저장함(설정은 파일로 — NVS 아님 원칙).
  - "끊김" 판단 기준(무엇을 몇 초 못 받으면 끊김인지)은 구현 설계 때 정함.
- 상시 전원이라 딥슬립 없음(센스·캠과 다름).

## 5. 할 일 순서(제안)

1. 프로토콜: 브릿지 번호·번호별 CAN ID(공용 헤더), 콘의 브릿지별 상태, 노드 ↔ 브릿지 기록, 기기 종류로 응답 브릿지 선택.
2. 채널: `CAN_CTRL_SET_CHANNEL` 구현(콘·브), AP 채널에서 두 브릿지 채널 계산, AP 변경 시 지연 후 이동.
3. 재브를 새 펌웨어(번호 0)로 — 지금과 똑같이 동작하는지 확인.
4. 보브 하드웨어 도착 후 번호 1 빌드, CAN 데이지 체인 연결(종단 저항 위치 확인).
5. 보릴 펌웨어(XIAO), 콘 화면(보릴 상태·켜기/끄기·끊김 시간 설정).
