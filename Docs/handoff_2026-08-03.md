## 오늘 세션 요약 — ESP-NOW 사진 전송 신뢰성 재설계

CAM→Cntl 사진 청크 전송이 "30cm 근거리인데도" 자주 실패하는 문제를 하루 종일 팠음.
찾아서 고친 진짜 버그들(추측 아니라 실기 로그/크래시 백트레이스로 확인):

1. **keepalive-청크 ACK 오귀속 레이스**: `send_cb`가 "어느 esp_now_send() 호출의
   완료"인지 구분할 방법이 API에 없어서, 1초마다 도는 keepalive의 완료 콜백이 청크
   ACK로 잘못 소비되던 문제. → 근본 해결책으로 청크를 아예 "핸드셰이크처럼 기다리는"
   방식 자체를 버리고 **스트리밍(그냥 순서대로 보냄) + 종단간 NACK 기반 선택적
   재전송**으로 전면 재설계(사용자 설계 지시 — "신뢰도 높은 브로드캐스팅에서 쓰는
   방식"). `esp_now_link.h`에 `ESP_NOW_MSG_PHOTO_CHUNK_NACK` 추가, Cntl은 chunk_idx
   비트맵으로 빠진 것만 추적해서 NACK, CAM은 그것만 재전송(최대 3라운드).
2. **CAM `photo_transfer_task` 스택 오버플로우**: 목록조회(LIST) 처리 시 중첩 호출
   (`ids[500]` 두 번 + `file_entry_t all[500]`)이 12KB 스택을 넘겨서 크래시 →
   `assert failed: xTaskRemoveFromEventList` → CAM 재부팅. Cntl 쪽엔 그냥 "무응답
   타임아웃(3006/3007)"으로만 보여서 오래 헤맴. 24KB로 증설.
3. **`ESP_ERR_ESPNOW_NO_MEM`**: 청크를 2ms 간격으로 스트리밍하니 드라이버 내부
   송신큐가 못 따라가서 33번째 청크쯤부터 대부분 즉시 거부됨(무선 유실이 아니라
   큐잉 자체가 실패). 로그로 직접 확인. → 큐 꽉 참 감지 시 짧게 대기 후 같은 청크
   재시도, 페이싱도 2ms→4ms로 늘림.
4. **CAM 채널락 레이스**: `advertise_timer_cb`(300ms 주기)가 채널을 바꾸는 것과
   `recv_cb`가 ADVERTISE_ACK 처리하는 타이밍이 겹치면 엉뚱한 채널에 락됨(Cntl은 항상
   CH1인데 CAM이 CH2로 락되는 게 반복 재현). `info->rx_ctrl->channel`(실제 수신
   채널)을 쓰도록 수정.
5. **Cntl HUB_RESET 타이밍 레이스**: 사용자의 실제 워크플로우는 "매번 소프트리셋 →
   연결 → 목록 → 사진"인데, HUB_RESET을 "공유기 완전 연결 후"에 보내다 보니 공유기
   재연결이 느릴 때(인증 backoff) 방금 막 새로 페어링된 CAM을 "예전 페어링"으로
   오인하고 걷어차버림. HUB_RESET을 ESP-NOW 켜지는 부팅 극초반(공유기 연결과 무관)
   으로 옮김 — 사람이 화면을 터치할 수 있는 어떤 시점보다 항상 먼저 나가게.
6. **Cntl PAIR_ACK 핸들러**: `became_paired`가 매 keepalive마다 true로 잡혀서
   SET_TIME을 1초마다 무한 재전송하던 버그 — false→true 전환(edge)일 때만 true로
   수정.
7. **Cntl 수신단 락 범위**: `esp_now_photo.c`의 `handle_meta`/`handle_chunk`가
   `s_state`만 짧게 락 걸고 `s_file_id`/버퍼쓰기는 락 밖에서 하던 것 — 관련 필드
   전부를 하나의 임계구역으로 통일(사용자 지적: "CNTL 수신단 구현이 이상한 것 같아").
8. Cntl UI: 선택(reconcile_selection)이 Model을 직접 읽어 반응하도록 재구조화(탭은
   Model만 바꾸고 액션은 Model 변화에 반응), 캐시 재사용 개념 완전 제거(선택 바뀌면
   무조건 새로 받음 — 사용자 명시적 설계 결정), WiFi 절전 끔, 목록 0장일 때 "사진
   없음" 표시, 목록갱신도 진행팝업+타임아웃 토스트로 통일.

### 현재 상태 — 검증 안 끝남

마지막 실기 테스트(오늘 마지막 CAM 재플래시 이후)에서 사용자가 "3006인데 잘 들어"
(진행 속도는 정상으로 보이는데 결국 3006으로 끝남)라고 보고한 직후, PC 이전 요청이
와서 **로그 캡처를 다시 시작하려던 참에 중단됨**. 즉 NO_MEM 재시도 수정은 청크가
훨씬 빨리/안정적으로 나가는 것까진 확인됐지만, 왜 그래도 최종적으로 3006(무응답
타임아웃)으로 끝나는지는 아직 원인 미확정 — 유력한 다음 가설: 청크는 다 갔는데
DONE 또는 NACK 라운드 처리 쪽에서 걸리는 것. **새 PC에서 재개할 때 여기부터
이어가면 됨**: CAM 시리얼(COM 포트, 아래 참고)을 열어서 `CKPT:` 로그를 보면서
가져오기 테스트 한 번 더 해보는 것부터 시작.

체크포인트 로그(`CKPT:` 접두어)가 CAM `send_one_photo()`/`resend_chunks()`
곳곳에 심어져 있어서, 어디서 막히는지 바로 보임 — 이번 세션에서 실제로 이 로그
덕분에 NO_MEM 버그를 찾았음. 계속 이 방식(시리얼 백그라운드 캡처하면서 사용자에게
"지금 테스트해주세요" 요청)으로 진행하면 됨.
