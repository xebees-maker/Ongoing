※ 이 문서는 지난 세션(handoff_2026-08-11.md 이후) 미커밋 상태로 쌓여있던 작업 전체를 다룸.

[ 한 일 ]

1. 사진 가져오기 3002(청크 누락) 버그 — 진짜 코드버그였음
   - 처음엔 무선손실률이 높다고 오판(resend_chunks 로그를 첫 전송과 재전송 구분 없이 읽은 탓).
     사용자가 "코드버그지"라고 단정, 재조사.
   - 진짜 원인: handle_meta()가 META 수신마다 무조건 비트맵을 리셋하는데, META 자체가
     unreliable로 3번 중복 전송되던 구조라 경쟁상태가 났던 것. META를 reliable
     요청(esp_now_reliable_request) 1회로 바꾸고, Cntl이 META_ACK를 보내도록 프로토콜에
     msg_type 45 신설(ESP_NOW_MSG_PHOTO_META_ACK). SR 자체가 가드 역할을 하므로 별도
     중복방지 가드는 불필요(사용자 판단).
   - 별도로 NACK 라운드 off-by-one도 발견+수정 — handle_done()이 라운드 증가를 비교 "후"에
     하고 있어서 Cntl이 CAM보다 항상 한 라운드 더 기다렸음. 증가를 비교 "전"으로 이동.

2. 진행팝업 재진입 버그 — "연결해제가 안 먹는 것처럼" 보이던 원인
   - 사용자 요청으로 시퀀스 다이어그램을 그려서 플로우 확인 → show_progress_popup()이 이미
     열려있는 팝업 위에 또 열리면서 깨졌던 것. 여는 함수 맨 앞에 "이미 열려있으면 먼저
     닫기" 가드 추가로 해결.

3. 지금촬영(캡처) 핸드셰이크 재설계 — 다단계+단계별 타임아웃
   - 배경: 무선 왕복시간용 타임아웃 하나를 카메라 하드웨어 초기화/촬영 대기에도 그대로
     재사용하던 게 "코드 스타일 문제"라는 지적.
   - CAM_CAPTURE_STATUS를 RECEIVED(0)/SUCCESS(1)/FAILED(2)에서
     INIT_NEEDED(3)/INIT_DONE(4)/CAPTURING(5)까지 확장, 카메라가 이미 준비돼 있으면
     INIT 단계는 건너뜀. 단계별로 CAM_CAPTURE_HW_TIMEOUT_MS(15초, 하드웨어 대기용)와
     기존 무선 타임아웃을 분리해서 적용.

4. 페어링 회귀 버그("한번에 안 되고 두번째에 됨") — 나이키스트 샘플링으로 원인 규명
   - 채널스캔 타이밍, COM5 플리커, 응답성 티어, CNTL WiFi 불안정 등 여러 가설을 사용자가
     구체적 근거로 전부 반박한 뒤, 사용자가 직접 나이키스트 정리를 적용해서 도출한 결론:
     CAM이 "명령 받을 수 있는 시간 3초 / 못 받는 시간(딥슬립 등) 4.8초" 주기로 살아있는데,
     CNTL의 PAIR_REQUEST 재시도 총 구간(span)이 그보다 짧아서 위상에 따라 CAM이 깨어있는
     타이밍을 못 맞추는 경우가 있었던 것.
   - 안전한 재시도 구간 = CAM의 "죽어있는 시간"의 2배(주기 전체가 아니라). CAM/Sens 공용
     헤더에 ESP_NOW_NODE_UNPAIRED_RETRY_SEC=3 신설, CNTL의 PAIR_REQUEST 재시도 횟수를
     (3*1000*2)/500ms + 1 = 13회(~6.5초 구간)로 계산식화. 실기 반복 테스트로 확인
     ("페어링은 완벽").

5. 5005(httpd_start 실패) + 내부(비-PSRAM) DRAM 크런치 — 근본원인 규명
   - 초기 가설(IP 수신 타이밍) 적용 후에도 5005가 재현되어 기각. 사용자 지시로 초기화
     루틴 각 단계에 SUCC/FAIL 로그를 심어서 재조사.
   - idf_size.py --archives/--files로 링커맵 분석 → libmain.a(Cntl 자체 코드)가 내부 DRAM
     .bss를 21,248바이트나 먹고 있었음(WiFi net80211 버퍼의 거의 3배) — httpd_start 시점
     free internal DRAM이 1,111~1,419B까지 떨어짐. HTTPD_DEFAULT_CONFIG()가
     task_caps=MALLOC_CAP_INTERNAL 고정이라 태스크 스택 할당이 실패했던 것.
   - 최대 offender였던 함수-로컬 static 버퍼(ui_main.c의 snapshot[3072], 전역이 아니라
     감사 시 놓치기 쉬움)와 ui_log.c의 s_buf[6144]를 비롯해, s_power_log_buf,
     s_current_list, s_dash_nodes/_prev, s_camera_nodes/_prev, esp_now_photo.c의
     s_list_items까지 전부 heap_caps_malloc(..., MALLOC_CAP_SPIRAM)으로 이전.
   - httpd_config_t.task_caps도 MALLOC_CAP_SPIRAM|MALLOC_CAP_8BIT로 명시 오버라이드.
   - 결과: libmain.a .bss 21,248B → 5,175B, 같은 부팅 시점 free internal DRAM
     1,300B대 → 15,063B(약 10배). 실기 3회 연속 측정으로 확인(8208B → 15063B).
   - 부수로 보고된 WiFi "채널 춤춘다"/사진가져오기 120초 지연 현상도 같은 RAM 압박이
     원인일 가능성 있음 — 아직 재검증 안 됨(다음 세션 할 일 참고).

     지적("이게 벌써 4번째야"). ui_strings.h에 STR_LABEL_WEB/STR_LABEL_MEMORY 정식

7. 통계탭 로그 스크롤 성능 전면개선 (오늘의 메인 작업)
   - 증상: 상황판/설정탭은 스크롤이 부드러운데 통계탭(일반로그+전력로그)만 페이지/판넬
     내부 스크롤 둘 다 심하게 느림.
   - 원인 진단(사용자가 직접 4가지로 정리, 전부 코드로 검증):
     라벨 하나에 최대 6KB까지 누적된 텍스트를 LV_LABEL_LONG_WRAP으로 그리는데, 이 모드가
     매번 전체 텍스트를 커스텀 TinyTTF(NanumGothic) 폰트로 글자 폭을 재가며 재배치하는
     비용이 큼. 일반로그(24pt)와 전력로그(18pt)가 폰트 크기도 다름.
   - 확정된 개선안(사용자 설계):
     1) 로그를 전부 영문으로 바꿔서 LVGL 내장 비트맵 폰트(측정 불필요, 훨씬 빠름) 사용 가능하게.
     2) 일반/전력 로그 폰트 크기를 20pt로 통일(Montserrat).
     3) 캡(용량 제한)은 기존 바이트 기준 그대로 유지 — 확인해보니 관련 버퍼 3개가 이미
        전부 PSRAM(5번 항목 작업 때 옮겨놨음)이라 internal 메모리 부담 없음, 코드 변경 없음.
     4) wordwrap을 완전히 제거. 팝업(클릭시 확장)은 보류 — 대신 우리 코드가 직접 폰트
        기준 픽셀폭을 재서, 폭을 넘는 줄만 끝을 잘라내고 "..."을 붙여 저장(LVGL의
        LONG_DOT처럼 라벨 전체 기준이 아니라 줄 단위로 개별 처리).
     5) (추가) 타임스탬프 포맷 통일 — ui_log.c에 공용 함수 ui_log_format_timestamp()
        신설, 일반/전력 로그 양쪽이 이 함수 하나만 호출해서 "[mm:ss] "를 붙임(기존엔
        전력로그만 자체 구현하고 있었음).
   - 구현: trim_to_width()/trim_multiline_to_width()(ui_main.c) — lv_font_get_glyph_width()로
     글자별 누적폭 계산(로그가 전부 ASCII라 UTF-8 디코딩 불필요), 넘치면 잘라서 "..." 추가.
     표시 직전(리프레시 타이머)에만 적용, 원본 누적버퍼는 그대로 둠. 로그 라벨
     long_mode을 WRAP -> CLIP으로, 폰트를 ui_font_get(TTF) -> &lv_font_montserrat_20으로 교체.
   - 로그 메시지 원문 전환: esp_now_photo.c(25곳), ui_main.c(29곳), main.c(7곳),
     ui_font.c(4곳), esp_now_hub.c(2곳), device_config.c(1곳) = 총 68곳 전부 영문으로.
     별도 팝업용 에러/워닝 설명 테이블(s_err_table/s_warn_table)은 이번 범위에서 제외.
   - 빌드 통과 확인 후 앱 파티션만 플래시(0x10000, assets 파티션 안 건드려서 설정 유지),
     실기 확인: "아주 다 잘 동작해"(사용자 확인) — 다만 "..." 트림은 마침 긴 줄이
     안 나와서 실기로는 아직 미확인.
   - 부가 문답(코드 정확성 확인용): 상황판/설정탭은 여전히 커스텀 TTF 18pt 그대로(짧은
     단일줄이라 WRAP 자체를 안 쓰고 있어서 원래 느릴 이유가 없었음 — 폰트 종류 자체가
     아니라 "큰 텍스트뭉치+WRAP 재측정 반복"이 병목이었다고 명확히 정리). 로그를 다시
     TTF로 되돌려도 WRAP 제거 효과는 그대로 남지만, trim_to_width()의 글자별 폭조회가
     TTF에서는(캐시미스 시) 래스터라이즈를 동반해 비트맵 폰트보다 약간 더 느릴 것이라고
     답변.
