== 2026-07-17 작업 요약 (Sens 단일-센서 헤드리스 노드 패밀리 + SCD41/LED 후속) ==

[ 오늘 삽질한 것들 ]

1. idf.py가 이 환경에서 아예 안 됨
   - idf.py가 자기 나름대로 python venv 경로를 다시 계산하는데(C:\Users\Dev\.espressif\
     python_env\idf6.0_py3.14_env), 이 경로가 실제로 없음. IDF_PYTHON_ENV_PATH 환경변수를
     줘도 무시함
   - cmake/ninja를 직접 호출하는 방식으로 우회. 처음엔 ccache를 PATH에 안 넣어서
     "CreateProcess failed: The system cannot find the file specified" 라는, 컴파일러가
     없다는 것처럼 보이는 헷갈리는 에러를 만남 — 실은 ccache wrapper가 없어서였음
   - 게다가 riscv 툴체인 버전을 처음에 잘못 추측(esp-14.2.0_20241119, 존재하지 않는 폴더)
     해서 또 같은 에러를 봄 — esp-idf/tools/tools.json에서 실제 핀된 버전
     (esp-15.2.0_20251204)을 찾아서 해결

2. 새 컴포넌트 폴더를 추가했는데 빌드가 못 찾음
   - bsp_c3_pico, sensor_sht4x, status_led를 새로 만들었는데 기존 build 디렉토리가 인식을
     못 함 — CMake가 컴포넌트 디렉토리 스캔 결과를 캐싱해서, 증분 재구성("Re-running
     CMake")만으로는 새 폴더가 안 잡힘
   - CMakeCache.txt + CMakeFiles를 지우고 완전히 새로 configure해야 잡힘. 처음엔 build
     디렉토리 전체를 지우려다 파일 락(Device or resource busy)에 걸려서 애먹음 — 결국
     내용물만 비우고 디렉토리는 남긴 채 재구성

3. idf_component_register(REQUIRES ...)를 Kconfig로 조건부로 갈랐는데 항상 한쪽만 적용됨
   - SRCS는 CONFIG_SENS_BUILD_HEADLESS에 따라 제대로 갈리는데, REQUIRES는 계속
     else() 쪽(레거시)으로만 잡힘 — sensor_node.c는 컴파일 목록에 있는데 그게 필요로
     하는 bsp_c3_pico.h를 못 찾는 이상한 상태가 됨
   - project_description.json을 까서 main 컴포넌트의 실제 resolved reqs를 보고서야
     원인 파악: ESP-IDF가 REQUIRES를 sdkconfig가 다 로드되기 전 "조기 확장" 단계에서
     한 번 평가해버려서, 그 시점엔 CONFIG_* 값이 없어 항상 else()로 감. SRCS는 이후
     실제 빌드 단계에서 다시 평가되니 문제가 없었던 것
   - 해결: REQUIRES는 조건부로 가르지 말고 두 빌드 타깃 필요 컴포넌트의 합집합으로
     고정, SRCS만 조건부로 가름

4. SCD41 stale 버그 진단이 두 번 뒤집힘
   - 처음엔 CRC 불일치 경로가 두 워치독(note_failure/check_stale) 어디에도 안 걸리는
     실제 코드 버그를 찾아서 고침(이건 진짜 버그였고 고친 게 맞음)
   - 근데 사용자가 "CO2만 계속 0, 온습도는 복구된다"는 더 자세한 증상을 알려줘서
     다시 보니, 셋 다 같은 I2C 트랜잭션에서 한 번에 읽히는 구조라 CRC 버그로는 그
     패턴이 설명이 안 됨 — 재분석 결과 "재초기화 직후 한 번만 살아나고 곧 다시
     죽는" 패턴으로 보여서 하드웨어 결함 쪽으로 무게를 실어서 설명했는데, 결국
     사용자가 확인한 실제 원인은 배선 접촉불량이었음. 진단 과정 자체는 합리적이었지만
     최종 원인은 완전히 다른 데 있었던 케이스

[ 잘 찾아낸 것들 ]

1. 큰 리팩터링 전에 플랜 모드로 먼저 들어가서 전체 구조(프로토콜/빌드구조/컴포넌트
   목록)를 문서화하고 승인받은 뒤 구현 시작 — 26개 파일, 6개 신규 컴포넌트/파일이
   걸린 변경이었는데 방향을 안 잃고 끝까지 감

2. LED 설계에서 "계속 켜짐"(전력 낭비) vs "아무 표시 없음"(진단 불가) 딜레마를
   저듀티 heartbeat 깜빡임으로 풀어냄 — 게다가 "제어기가 점검모드를 원격 트리거"
   하자는 아이디어가 순환논리(ESP-NOW로 점검 신호를 받으려면 ESP-NOW가 이미
   되고 있어야 함)라는 걸 짚어서, 사용자가 바로 로컬 자율 판단 방식으로 방향을
   정할 수 있게 도움

3. 코드 수정할 때마다 실제로 ninja/cmake 빌드를 돌려서 검증 — 헤드리스 3개 센서
   타입 + 레거시 경로 + Cntl까지 5개 구성을 개별로 다 빌드 확인했고, 그 과정에서
   REQUIRES 버그도 실제로 걸려서 잡아냄(빌드 안 해봤으면 몰랐을 문제)
