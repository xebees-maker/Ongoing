   않고 실제 파일시스템 내용(ls, head)으로 직접 재검증한 뒤 커밋함 — git의 rename 휴리스틱은
   장식이고 실제 트리 상태가 진실이라는 걸 확인 절차로 챙김.

[ 반성할 점 ]

- 문서 안에서 "Cntl"처럼 프로젝트 애칭/기기 이름과 실제 폴더명이 같은 문자열을 공유할 때,
  경로가 명시된 단 하나의 문장(cntl_incremental_test/main/esp_now_hub.c)을 "예외"로 치부하지
  말고 오히려 "이게 진짜 힌트일 수 있다"로 먼저 의심했어야 함. 특히 레포에 정식/실험용
  프로젝트가 병렬로 존재하는 구조에서는, 서술형 문서보다 git log --stat이 항상 더 권위있는
  소스라는 걸 처음부터 우선순위에 뒀어야 함.
- 사용자가 직접 "지금 incremental 아니냐"고 물었을 때가 가장 싼 검증 타이밍이었는데, 그 순간
  git log 대신 기존 추측(핸드오프 해석 + 소스 주석)을 방어하는 답을 냄. 직접적인 정정성
  질문을 받으면 "왜 그렇게 생각하는지 설명"보다 "즉시 가장 권위있는 소스로 재검증"이 항상
  먼저여야 함.
- 소스 코드 주석의 "검증됨"이라는 단어를 문맥(부분 기능만 검증됐는지 전체가 검증됐는지) 확인
  없이 결론으로 사용함 — 주석은 작성 당시 시점의 부분적 사실일 수 있고, 그 이후 코드가
  포기됐는지 여부는 주석만으로는 알 수 없음(git log/커밋 메시지로 봐야 함).
- 하드웨어 의심을 두 번이나 반복한 것도 뼈아픔 — feedback-dont-relitigate-ruled-out-hardware
  메모리가 이미 있었는데 실시간으로 못 지켰음. 메모리를 "읽었다"와 "그 순간 적용한다"는 다른
  것이라는 걸 이번에도 확인함.
- 결과적으로 하루 대부분을 죽은 프로젝트(Cntl_old) 디버깅에 썼고, 정작 밀려있던 진짜 작업
  (ESP-NOW 사진 전송 3006 타임아웃 원인 규명)은 오늘도 전혀 진행 못 함 — 다음 세션 최우선
  순위로 넘어감.
