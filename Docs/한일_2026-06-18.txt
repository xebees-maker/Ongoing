== 2026-06-18 작업 요약 (ESP32-C6 sensor-c6 프로젝트) ==

[ 오늘 삽질한 것들 ]

1. DHT22 "센서 응답 자체가 없음" — 핀을 세 번이나 바꿔도 동일하게 실패
   - GPIO4 → 스트래핑 핀(VDD_SPI 전압 선택) 의심, 풀업 추가해봤지만 동일
   - GPIO7 → LP_I2C 고정 핀(SDA=6/SCL=7) 간섭 의심, 동일
   - GPIO8 → 부트 스트래핑 핀, 동일
   - gpio_reset_pin() 추가(IOMUX 강제 GPIO 전환)도 효과 없음
   - 타임아웃 100us→1000us, 샘플 간격 1초→3초로 늘려도 동일
   → 세 가지 핀 이론 모두 틀렸음(검증 없이 확신 있게 말한 게 문제였음)

2. GPIO 자체 동작 검증
   - GPIO8에 LED 연결, 1초 토글 테스트 → 정상 (출력 확인)
   - GPIO8 INPUT으로 두고 손으로 터치 → 레벨 변화 로그 정상 감지 (입력 확인)
   → GPIO 하드웨어 자체는 완전히 정상. 핀 문제가 아니라는 게 확정됨

3. 소프트웨어 로직 아날라이저로 진짜 원인 발견
   - 오실로스코프 없어서, GPIO 레벨 변화를 타임스탬프와 함께 배열에 기록하는
     캡처 코드를 임시로 작성해서 raw 파형을 로그로 재구성
   - 처음엔 "응답 끝난 후"만 캡처해서 10ms 내내 HIGH(무응답)로만 보임
   - 호스트의 시작 신호 자체부터 캡처하도록 바꾸자 — 실제로는 정상적인
     DHT22 응답(84개 전환, ~3.8ms, 40비트 패턴과 일치)이 잡힘!
   → 진짜 원인: `dht22_read()`가 호스트 시작 신호(LOW 2ms → HIGH 30us →
     INPUT 전환)를 인터럽트 켜진 상태로 보내고, 그 다음에야
     `portDISABLE_INTERRUPTS()`를 호출하고 있었음. 그 사이(호스트가 라인을
     놓아준 시점 ~ 인터럽트 끄는 시점) LVGL/SPI/터치 인터럽트가 끼어들면
     DHT22의 짧은 응답 윈도우(20~40us 내 시작)를 통째로 놓침.
   → 수정: `portDISABLE_INTERRUPTS()`를 시작 신호 보내기 *이전*으로 옮기고,
     `vTaskDelay(2ms)`(스케줄러 필요)를 `esp_rom_delay_us(2000)` busy-wait로
     교체 → 시작 신호~응답 polling 전체를 인터럽트 비활성 구간 하나로 묶음

4. 왜 S3에서는 같은 코드로 문제가 없었나
   - S3는 듀얼코어(Xtensa 240MHz), C6는 싱글코어(RISC-V 160MHz)
   - C6는 LVGL 화면 갱신(SPI DMA)·터치 I2C·tick 등 모든 인터럽트가 DHT22
     코드와 같은 코어에 몰려서, 취약한 틈(인터럽트 켜진 채 방치된 구간)에
     걸릴 확률이 훨씬 높았음. S3는 운이 좋았을 뿐, 같은 버그가 잠재해 있었음
   - S3(startup) 프로젝트도 같은 공유 컴포넌트(C:/Projects/components/sensor_dht22)
     를 쓰도록 이미 리팩토링되어 있어서, 이번 수정이 자동으로 같이 적용됨

5. SCD41 — i2c_new_master_bus 실패 (SDA pin can only be configured as GPIO#6)
   - I2C port 1이 C6에서는 LP_I2C(저전력 I2C) 컨트롤러로 매핑되고, SDA/SCL이
     GPIO6/7로 고정되어 있음을 에러 메시지로 확인
   - 추가로 클럭 소스 에러도 발생: "the clock source does not support lp i2c"
     → `I2C_CLK_SRC_DEFAULT`(XTAL)는 LP_I2C가 지원 안 함, ESP-IDF 헤더
     (`clk_tree_defs.h`) 확인해서 `LP_I2C_SCLK_DEFAULT`(RTC_FAST)로 교체
   → SDA=GPIO6, SCL=GPIO7 + 클럭 소스 수정 후 정상 동작 (CO2 ~741~751ppm)

[ 잘 찾아낸 것들 ]

1. GPIO 출력/입력을 분리해서 검증하는 진단법
   - LED 토글 테스트(출력 검증) + 터치 감지 테스트(입력 검증)로 "핀 자체는
     멀쩡하다"를 먼저 확정짓고, 그다음 타이밍 문제로 좁혀나간 접근이 유효했음

2. 오실로스코프 없이 소프트웨어로 파형 캡처
   - 인터럽트 비활성화 구간에서 레벨 변화+타임스탬프를 배열에 기록 → 끝난 후
     한꺼번에 로그 출력하는 방식으로 실제 마이크로초 단위 파형을 재구성함
   - 호스트가 보내는 시작 신호까지 포함해서 캡처해야 진짜 원인이 보임
     (응답 구간만 캡처하면 "무응답"으로 오인하기 쉬움)

3. DHT22 핵심 버그: portDISABLE_INTERRUPTS() 호출 시점
   - 타이밍에 민감한 비트뱅킹 프로토콜은 "시작 신호 송신부터 응답 polling
     까지" 전체를 인터럽트 비활성 구간으로 감싸야 함. 일부만 감싸면 핀을
     아무리 바꿔도 똑같이 실패함(핀 문제처럼 보이지만 사실은 타이밍 구조 문제)

4. SCD41 LP_I2C 고정 핀 + 클럭 소스
   - I2C port 1 = LP_I2C, SDA=GPIO6/SCL=GPIO7 고정, 클럭 소스는
     LP_I2C_SCLK_DEFAULT(RTC_FAST) 사용해야 함 (I2C_CLK_SRC_DEFAULT=XTAL 불가)

5. 두 센서(DHT22/SCD41) 온습도 비교 디스플레이 추가
   - SCD41도 온습도를 같이 주므로 화면에 SCD-T/SCD-H 행 추가, DHT22와
     나란히 비교 가능하게 만듦

[ 반성할 점 ]

- 핀을 세 번 바꾸는 동안, 매번 "이게 원인입니다"라고 검증 없이 확신 있게
  말했다가 다 틀렸음 (스트래핑 핀, LP_I2C 간섭, 부트 스트랩 이론)

  재확인을 요청함 — 정작 원인은 사용자 하드웨어가 아니라 내가 짠 코드의
  인터럽트 처리 순서였음
→ 다음부터는 같은 종류의 추측이 두 번 틀리면 추가 추측 대신 바로 실측
  (소프트웨어 로직 아날라이저 등)으로 전환하기로 함
