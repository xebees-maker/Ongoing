3. SLEEP_NOW 타이밍 프로토콜 전면 재설계 (사용자 상세 설계 지시)
   - 예전엔 CAM_CONFIG_ACK를 계기로 SLEEP_NOW를 보냈는데, 사용자 의도는 "CONFIG_ACK는 CNTL을
     busy로만 만들고, 진짜 슬립 결정은 오직 (a) CNTL의 적응형 idle 타이머 만료 (b) CAM의
     웨이크 보고 두 시점 중 나중에 오는 쪽"이어야 한다는 것 — esp_now_hub.c에 별도
     `esp_timer` 기반 적응형 데드라인 타이머 신설(`esp_now_hub_note_user_action()`이 매번
     stop+start_once로 리셋).
   - CAM은 절대 스스로 자지 않고 항상 SLEEP_NOW를 기다림 — 예전의 "페어링 대기 15초 못
     찾으면 포기 후 응답성 간격만큼 통째로 잠" 방식과 "70초 무통신시 자율 취침 폴백"을 전부
     제거하고, 대신 5초마다 `SLEEP_NOW_REQUEST`(재요청)를 보내며 계속 깨있는 걸로 교체.
     CNTL은 이 재요청을 받으면 워닝을 남기고 다시 시도, 3회 넘게 반복되면 에러로 격상.
   - 응답성 프리셋에 "즉시"(값 0 = Live, 딥슬립 자체를 안 함) 신설. 기존엔 1초가 최소값
     이었던 걸 0으로 교체.
   - ui_log.c/.h에 기존 ERROR(적색, 재부팅 전까지 유지)와 별개로 WARNING(황색, 팝업 확인
     즉시 자동 소거) 체계 신설 — 로고 아이콘도 ERROR 있으면 적색, 없고 WARNING만 있으면
     황색으로 분기.
   - 실기 dual-serial 캡처로 설계한 시퀀스(PAIR_ACK→SET_TIME→CONFIG_SET→CONFIG_ACK→
     SLEEP_NOW(동시)→DEEP_SLEEP_STATS(2ms 뒤)) 그대로 재현되는 것까지 확인.

4. 목록가져오기(3007) 버그 — 프로토콜 근본 재설계
   - 증상: 페어링 직후 자동 목록가져오기는 항상 성공, 수동 목록가져오기 버튼은 항상 3007
     (무응답) 실패. 사용자가 직접 원인 추정 — CAM이 파일마다 `cam_storage_stat()`을 또
     불러서(이미 스캔 때 얻은 정보를 재조회) SD I/O가 느렸고, 게다가 목록 항목을 파일당 1개씩
     unreliable로 쐈던 게 근본적으로 불안정했다는 것.
   - 사용자 설계대로 전면 교체: PHOTO_LIST_COUNT(총 개수 먼저, reliable) →
     PHOTO_LIST_BATCH×N(항목 최대 64개씩 묶어서 reliable) → PHOTO_LIST_DONE(단순 완료 신호).
     배치 자체가 reliable이라 사후 재전송/비트맵 추적이 통째로 불필요해짐 — 예전
     Selective Repeat 방식(2026-08-10 도입) 완전 폐기.
   - 에러 조건 2가지: (1) DONE이 이미 아는 개수보다 적게 받은 상태로 조기 도착 → 즉시
     PHOTO_LIST_ERROR를 CAM에 reliable로 통보, CAM은 상태 정리 후 대기 복귀. (2) 다 받았는데
     DONE이 안 옴 → 별도 처리 불필요, 기존 "마지막 진행 이후 경과시간" 정체감지가 그대로 잡음.
   - CAM 쪽 `cam_storage_list_full()` 신설 — 기존 스캔(`scan_all_files`)이 이미 stat()으로
     갖고 있던 mtime/size를 그대로 재사용해서 파일마다 추가 조회를 없앰(raw FatFs
     `f_opendir`/`f_readdir`로 stat() 자체를 없애는 더 근본적인 최적화는 사용자 지시로 보류).
   - `esp_now_link.h`에 신규 구조체(`esp_now_photo_list_count_t`/`_item_t`/`_batch_t`) 추가,
     예전 `esp_now_photo_list_entry_t`(unreliable 1건)와 SR용 missing_idx 필드는 제거.
   - Cntl 쪽 이름 충돌 발견+정리: 새 wire 구조체 `esp_now_photo_list_item_t`가 Cntl 로컬 UI용
     구조체와 이름이 겹쳐서, 로컬 쪽을 `esp_now_photo_list_view_item_t`로 개명.
   - 실기 검증: 309개 파일 COUNT→BATCH(64×4+53)→DONE까지 약 150ms 만에 완주, 수동/자동
     둘 다 반복 테스트 통과 — 3007 재현 안 됨.

5. 오늘의 큰 버그 헌트 — 응답성(response_interval)이 "즉시" 대신 계속 2로 보고됨(I=2)
   - 처음엔 "버그 아니고 예전에 저장된 값이 남은 것뿐"이라고 성급하게 결론 — 사용자가
     "항상 live로 쓴다고 이미 두 번 말했다"며 강하게 반박, 남 의심 말고 최근에 내가 건드린
     코드부터 보라고 지적. 정확한 지적이었음(아래 [ 반성할 점 ] 참고).
   - 실제 원인: `device_config.c`의 `DEVICE_CONFIG_VERSION`을 이전 세션(2026-08-10)에 1→2로
     올리면서(adaptive_response_sec 필드 추가) 마이그레이션 없이 "버전 불일치 시 기본값
     폴백"만 해뒀음. 그 폴백이 걸렸던 부팅 중 다른 설정(촬영주기 등)을 하나라도 Apply하면,
     `device_config_save()`가 세 필드를 항상 통째로 저장하는 구조라서 그때 램에 남아있던
     응답성 기본값(2)까지 새 버전 파일에 같이 영구 저장돼버림 — 그 이후로는 파일이 "정상
     버전"이라 계속 그 잘못된 2를 그대로 로드.
   - 재발방지 코드 추가: 버전 불일치 폴백 시 기존엔 `ESP_LOGW`만 남기던 걸,
     `UI_ERR_CONFIG_FILE_MISMATCH`로 화면에도 반드시 보이게 함.
   - 부수 발견 버그: 사용자가 "즉시 Apply 버튼이 disable 되어있다"고 지적 — 촬영주기/응답성/
     적응형반응 Apply 버튼 3개 전부, 화면 생성 시 "부팅 직후엔 표시값==저장값"이라는(이번
     경우처럼 저장된 값이 프리셋 목록에 없으면 틀리는) 가정으로 무조건 비활성화 고정해놓고
     실제 일치 여부로 판정하는 로직(`update_*_apply_enabled()`)을 안 불렀던 것 — 셋 다
     생성 직후 그 함수를 호출하도록 수정.
   - 응답성 즉시(0) 재적용 후 30초 캡처로는 부족하다는 사용자 지적(적응형반응이 5분(300초)
     설정이라 그 안엔 당연히 조용함) — 330초(5.5분) 캡처로 재검증, 5분 임계값을 넘긴 뒤에도
     SLEEP_NOW가 전혀 안 나가는 것 확인(Live 가드가 적응형 타이머 만료보다 우선 동작).

6. 목록가져오기 팝업 2단계 UI 신설
   - 사용자 요청: "가져오기 명령 전송 / 목록 수신 중 / 목록 수신 성공(실패)" 세 문구가
     단계별로 뜨게 해달라는 것. 지금촬영 팝업(`capture_popup_tick_fn`)과 동일한 2줄 스택
     라벨 구조로 구현.
   - `esp_now_photo_list_state_t`에 ERROR 상태 신설(기존엔 실패해도 IDLE로만 돌아가서 팝업이
     실패 사유를 알 방법이 없었음), `esp_now_photo_list_count_received()` getter 신설
     (COUNT 응답 여부로 "명령 전송" 단계 완료 판정 — 단순히 total>0으로 판정하면 CAM 파일이
     0개인 경우(모두지우기 직후) 오판하는 문제가 있어서 별도 플래그로 분리).
   - 배치화 이후 전체 전송이 150ms 안팎이라 원래 속도로는 단계 전환이 안 보여서, 확인
     목적으로 각 단계 최소 500ms 노출 딜레이를 임시로 넣어 실기로 확인(사용자 확인:
     "잘 된다") → 확인 끝난 뒤 사용자 지시로 딜레이 전부 제거, 실제 속도로 복원.

[ 반성할 점 ]

- 오늘 가장 큰 실수: 사용자가 이미 "항상 live로 테스트한다"고 두 번 말한 상태에서, I=2
  증상을 보고 첫 결론으로 "버그 아니라 저장된 값이 남은 것"이라고 단정지었음 — 사용자의
  명시적 전제를 의심하고 안 맞는 설명(사용자가 뭔가 안 했을 것)부터 찾은 게 잘못. 실제
  원인은 내가 직접 만든 버전범프 마이그레이션 누락이었음. 사용자가 "몇번째냐", "사람이었으면
  벌써 죽었어"라고 할 정도로 반복된 패턴이라고 지적 — `user_experience_level` 메모리에
  2026-08-11 재발 사례로 상세 기록함: 사용자 진술과 증상이 충돌하면 진술을 사실로 놓고 내
  최근 코드부터 감사할 것.
- Apply 버튼 disable 문제도 처음엔 "드롭다운을 즉시로 바꾸고 Apply 누르라"고 안내했는데,
  실제로는 버튼 자체가 코드 버그로 비활성화돼 있어서 사용자가 누를 수조차 없었음 — 코드를
  다시 안 보고 UI 사용법 설명으로 넘어가려 한 것도 같은 계열의 성급함.
- 5분(적응형반응) 검증에서도 처음엔 30초 캡처로 "조용하니 안정됐다"고 결론지었다가, 사용자가
  "5분 설정인데 30초로 뭘 아느냐"고 지적 — 검증 시간 단위를 실제 관련 설정값과 맞춰야 한다는
  걸 다시 확인.
