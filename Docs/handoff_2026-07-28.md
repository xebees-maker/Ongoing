# Handoff — 2026-07-28

이어서 볼 것: `Docs/handoff_2026-07-19.md`(Sens 배선검증+절전1단계) 이후 CAM 프로젝트로 넘어온 세션.
이번 건은 2026-07-20~07-28에 걸쳐 이어진 CAM(ESP32-S3 카메라 노드) corruption 조사 마무리 +
프로덕션 복원 + ESP-NOW 확장. 자세한 기술적 근거는 메모리
`project_cam_dvp_corruption_investigation` / `project_cam_esp_now_production`에 다 있음 — 여기는
요약만.

## 오늘 한 일 — CAM corruption 완전 해결 + 프로덕션 파이프라인 복원 + ESP-NOW 확장

### 1. CAM 사진 corruption의 진짜 원인 확정 (며칠간 하드웨어/DVP를 의심했던 게 전부 틀렸음)

- **버그 #1**: `esp_console_new_repl_usb_serial_jtag()`가 내부적으로 LF→CRLF 치환을 켜둬서,
  JPEG 바이너리 전송 중 0x0A 바이트가 전부 0x0D 0x0A로 부풀려짐 — 크기는 안 변한 것처럼 보이면서
  (호스트가 원본 길이만큼만 읽어서) 내용만 밀렸음. 마커류는 살아남고 엔트로피 데이터만 깨져서
  "컨테이너는 멀쩡한데 픽셀만 깨진" 증상이 나온 이유.
- **버그 #2**: 버그 #1 고친 뒤에도 큰 파일(5MP)에서 비결정적으로 또 깨짐 — USB-Serial-JTAG
  드라이버가 콘솔/로그용으로 설계돼서, TX 링버퍼(256바이트)가 밀리면 조용히 바이트를 버리면서도
  `fwrite`엔 항상 "전부 성공"으로 보고함. `usb_serial_jtag_write_bytes()`를 직접, 200바이트
  단위로 청크 나눠 호출하도록 고쳐서 해결(반환값 정직하게 확인).
- **하드웨어는 처음부터 문제 없었음** — Waveshare 공식 UVC 예제로 두 보드 다 깨끗하게 나온 게
  "돌파구"였는데, UVC가 이 콘솔 코드 자체를 안 타서 우연히 깨끗했던 것뿐. 결국 사용자가
  "네가 이미 아니라고 확인한 걸 왜 자꾸 다시 의심하냐"고 지적한 게 정확했음.

### 2. 두 센서 각자 최대 해상도 확정 + 안정화

- OV5640(COM5): 5MP(2592x1944), XCLK 24MHz, fb_count 1 — 20MHz론 5MP 자체가 아예 실패(NO-SOI/
  NO-EOI 반복). `esp32-camera`의 `FB_GET_TIMEOUT`(4000ms→15000ms)도 같이 늘림.
- OV3660(COM17): QXGA(2048x1536), XCLK 20MHz, fb_count 2 — 중간에 "부팅 자체가 완전 무응답"
  증상이 나와서 한참 헤맸는데, 알고보니 실제 원인은 **물리적 USB 재연결이 필요한 상태**였음
  (esptool ROM 레벨은 계속 정상 응답해서 칩은 안 죽어있었음). XCLK/fb_count 문제가 아니었을
  가능성이 있음 — 완전히 갈라서 재현/반증은 못 함.
- 두 센서 다 실기에서 CRC32(촬영 직후=플래시 재읽기=PC 수신) 완전 일치까지 확인.

### 3. 격리 테스트 복원 → 프로덕션 경로

SD 저장, 카메라SCCB/IO익스팬더 공유 I2C 버스(`bsp_esp32s3_cam_init()`), WiFi(AP)+ESP-NOW 전부
복원(며칠 전 corruption 조사 때 자원경합 의심해서 꺼뒀던 것들 — 전부 무관했음이 확인됨). 임시
진단용이었던 플래시 파티션 저장/`getflash` 콘솔 명령/`cam_get.py getflash`는 다 삭제.

### 4. ESP-NOW 사진 전송 프로토콜 확장

기존 META→CHUNK*→DONE 청크 전송(청크당 ACK+3회 재시도) 구조는 그대로 살리고:
- `crc32` 필드를 실제로 채움(이전엔 TODO로 0 고정) — Cntl(`esp_now_hub.c`)도 재조립 후 CRC
  검증하도록 추가. "청크 개수 맞음 ≠ 내용 맞음"을 이번 조사에서 직접 겪어서 반영.
- `PHOTO_REQUEST_MODE_CAPTURE_NOW` 추가 — 기존 파일 대신 그 자리에서 새로 찍어서 보내는 모드
  (새 메시지 타입 없이 기존 구조 재사용). CAM/Cntl 둘 다 빌드 확인, **실제 Cntl 보드와 연동
  테스트는 아직 안 함** — 다음에 Cntl 붙이면 꼭 확인.
- CPU 160→240MHz. PSRAM은 이미 Octal 80MHz라 그대로.
- **Automatic Light Sleep 시도했다가 실기에서 콘솔이 완전히 멈춰서(4분+ 무응답) 되돌림.**
  Sens에서는 통했던 패턴인데 CAM은 USB-Serial-JTAG 콘솔+카메라 DVP가 있어서 안 맞는 듯 —
  다음에 재시도할 땐 light sleep 대신 WiFi modem-sleep만 따로 검토하거나, `esp_pm_lock`으로
  카메라/콘솔 사용 구간을 명시적으로 막는 식으로 다시 설계해야 함.

### 5. 한 소스로 두 센서 빌드 가능하게 정리

`main/Kconfig.projbuild`에 `CAM_SENSOR_VARIANT`(OV5640/OV3660) 선택 하나 추가 — XCLK/fb_count/
기본 해상도가 한 번에 갈림. 센서 바꿀 땐 이 값만 바꾸고 `cmake` 재구성(새 Kconfig라 `ninja`만으론
안 됨) 후 재빌드/재플래시. 리팩터링 후 두 센서 다 실기 재검증 완료.

### 6. 잡다한 삽질

- `cam_get.py`가 포트 열 때마다 항상 리셋된다고 믿었는데 실제로 안 그럴 때가 있음 — 회귀처럼
  보이는 3연속 실패의 진짜 원인이었음. 로그 타임스탬프가 안 작으면 리셋 안 된 걸 의심할 것,
  또는 `esptool chip-id`로 확실히 리셋.
- **CAM 프로젝트가 이번에 처음으로 git에 커밋됨** — 지금까지 전부 untracked 상태였음.
  `sdkconfig`/`managed_components/`는 레포 공통 `.gitignore`로 빠지는데, 그 안에 있는 벤더
  패치 2개(`Kconfig`의 JPEG 버퍼 기본값, `esp_camera.c`의 FB_GET_TIMEOUT)는 새로 체크아웃하면
  사라지는 문제라 `git add -f`로 예외적으로 강제 추적함. `CAM/sdkconfig.defaults` 새로 만들어서
  센서 선택/화질/CPU/플래시 크기 등 핵심값 재현되게 해둠.

## 다음 세션 참고

- **Cntl과 실제 ESP-NOW 연동 테스트 전혀 안 함** — CAPTURE_NOW 모드, CRC 검증, META→CHUNK→DONE
  전체가 CAM 단독으로만 확인됨. Cntl 붙이면 페어링부터 사진 수신까지 end-to-end로 확인 필요.
- **Cntl 쪽 사진 최종 처리 미정** — 지금은 CRC 확인하고 버퍼 그냥 free함. SD 저장? 웹 대시보드
  표시? 결정 안 됨.
- **저전력(light sleep) 재설계 필요** — 위 5번 참고, 지금은 꺼진 채로 둠.
- OV3660의 "24MHz에서 부팅 무응답" 증상이 진짜 XCLK 문제였는지 물리 USB 문제였는지 안 갈렸음 —
  급하지 않으면 그냥 지금 검증된 조합(20MHz/fb_count 2) 유지, 궁금하면 나중에 따로 확인.
- 화이트밸런스(보라색/초록색 색조) 튜닝은 이번 범위 밖으로 전혀 안 건드림.
