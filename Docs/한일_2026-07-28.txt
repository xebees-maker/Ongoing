== 2026-07-28 작업 요약 (CAM corruption 완전 해결 + 프로덕션 복원 + ESP-NOW 확장) ==

[ 오늘 삽질한 것들 ]

1. 며칠간 하드웨어/DVP 타이밍을 의심했던 게 전부 헛다리였음
   - 진짜 원인은 두 개: (1) USB-Serial-JTAG 콘솔의 LF→CRLF 자동 치환이 JPEG 바이너리를
     오염시킴, (2) 큰 파일에서 TX 링버퍼가 밀리면 fwrite가 거짓으로 "성공"을 보고하며
     바이트를 조용히 버림. 둘 다 콘솔/전송 레이어 문제였지 카메라/센서/DVP는 처음부터
     멀쩡했음
   - 사용자가 "UVC는 이 콘솔을 안 타서 깨끗했던 거고, 저장/전송 단계만 남았다"고 직접
     추론해서 방향을 잡아줬는데, 그 뒤로도 한동안 하드웨어 쪽으로 다시 돌아가려는 티를 냄

2. OV3660 QXGA 부팅이 갑자기 완전 무응답 (로그 한 줄도 없이)
   - XCLK 24MHz/20MHz, fb_count 1/2, 해상도 여러 조합을 다 바꿔봐도 계속 무응답
   - esptool로는 ROM 레벨에서 계속 정상 응답해서 칩이 죽은 게 아니란 건 알았는데,
     결국 사용자가 물리적으로 USB를 뽑았다 다시 꽂고 나서야 정상 부팅됨 — 그 시점에
     fb_count도 같이 바꿔서 정말 뭐가 원인이었는지 완전히 갈라내진 못함

3. Kconfig 리팩터링(센서 선택 하나로 통합) 직후 5MP 촬영이 3연속 실패
   - "리팩터링이 XCLK를 잘못 해석했나" 의심하며 코드/sdkconfig를 몇 번이나 다시 읽음
   - 진짜 원인은 전혀 다른 곳: cam_get.py가 포트 열 때마다 리셋된다고 믿었는데 이번엔
     안 걸렸던 것. 로그 타임스탬프가 23초→46초→114초로 계속 누적되는 걸 보고서야
     "이거 리셋이 안 된 거구나" 알아챔. esptool로 확실히 리셋 걸자마자 바로 정상

4. Automatic Light Sleep이 실기에서 콘솔을 완전히 멈춰버림
   - Sens에서 검증된 패턴을 그대로 가져왔는데 CAM에서는 shot/ls 명령이 4분 넘게
     무응답 — esptool ROM 레벨은 정상이라 칩이 죽은 건 아니고, light sleep이 USB
     콘솔이나 카메라 DVP 타이밍과 안 맞는 것으로 보임. 확인 즉시 되돌림

[ 잘 찾아낸 것들 ]

1. CRC32를 세 지점(촬영 직후/플래시 재읽기/PC 수신)에 찍어서 정확히 어느 경계에서
   깨지는지 좁힌 것 — "크기만 맞으면 안심"하던 습관을 버리고 전송 파이프라인 전체를
   체크섬으로 검증하는 방식으로 전환. 이후 ESP-NOW 전송에도 같은 원칙을 그대로 적용

2. USB-Serial-JTAG 드라이버 소스(usb_serial_jtag_vfs.c)까지 직접 읽어서 "콘솔용으로
   설계된 링버퍼가 큰 바이너리 전송엔 안 맞는다"는 근본 메커니즘을 정확히 짚어냄 —
   추측이 아니라 소스 코드로 확인하고 고침

3. 두 센서를 한 소스에서 Kconfig 선택 하나로 빌드하는 구조로 정리
   - 사용자가 "카메라만 바꿔 끼우면 되냐"고 물어서 "아니다, 컴파일타임에 갈라져 있다"고
     정직하게 답한 뒤, "그럼 소스는 하나로 관리해야 하지 않냐"는 요청에 맞춰 XCLK/
     fb_count/해상도가 센서 선택 하나로 다 맞춰지도록 리팩터링. 양쪽 다 실기 재검증

4. CAM 프로젝트가 이번 세션 내내 git에 한 번도 안 올라가 있었다는 걸 뒤늦게 발견하고,
   sdkconfig.defaults 없이 커밋했으면 벤더 패치 2개(Kconfig 기본값, FB_GET_TIMEOUT)가
   새 체크아웃에서 조용히 사라질 뻔한 걸 잡아서 git add -f로 강제 추적 처리

[ 반성할 점 ]

  끝까지 못 갈랐음 — 변수 하나씩만 바꾸는 원칙을 급할수록 더 지켰어야 함
- Kconfig 리팩터링 후 "3연속 실패"를 곧바로 회귀로 단정하고 코드를 의심했는데, 실제로는
  도구(cam_get.py) 쪽 문제였음 — 변경 직후 실패가 나오면 변경분과 도구/환경 둘 다
  의심 목록에 넣었어야 더 빨리 원인을 찾았을 것
- CAM이 이 세션 시작 시점까지 한 번도 커밋 안 된 채였다는 걸 훨씬 일찍 확인했어야 함 —
  중간에 날린 작업이 있었다면 복구 불가능했을 리스크였음
