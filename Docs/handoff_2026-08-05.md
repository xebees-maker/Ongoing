# Handoff — 2026-08-05

이어서 볼 것: `Docs/handoff_2026-08-04.md`(PC 이전) 이후, ESP-NOW 통신 신뢰성 3계층 재설계
(Layer 0/1/2) 착수 세션. Layer 0/1은 이번 세션에 끝까지 구현+실기검증+커밋까지 됨. 그 검증 도중
사용자가 지금촬영 기능의 오래된 버그(2026-08-02 to-do 1번)를 재현시켜서 잠깐 옆길로 새어 그것도
같이 고쳤음. 자세한 기술 배경은 메모리 `project_cntl_cam_esp_now_reliability_layers`,
`project_cntl_cam_capture_now_race_and_frame_lag` 참고 — 여기는 요약만.

COM 포트(이 세션 기준, 매 세션 재확인 원칙): **Cntl = COM12, CAM = COM13**.

## 오늘 한 일

### 1. Layer 0 — 채널 추적(esp_now_channelsync) 구현 + 검증

CHANNEL_PING/PONG 전용 메시지로 채널 추적을 페어링/앱 트래픽과 분리 — 채널이 바뀌어도 재페어링
없이 ~1.2초 안에 재동기화. 채널 강제 전환 테스트로 실기 검증 완료.

### 2. Layer 1 — Reliable 모드(esp_now_reliable) 구현 + 검증

`esp_now_reliable_request()` — 재시도 있는 블로킹 요청/응답. Layer 0 위에 얹음. 페어링/목록/촬영/
삭제 등 제어 메시지에 적용.

### 3. 3006(가져오기 무응답) 재발 — 원인 규명 + notify_alive() 수정

Layer 0/1을 실기 검증하던 중 "20번 정도 가져오기하니까 또 3006" 재현. ESP-IDF v6.0.2 소스를
직접 확인해서(Explore 서브에이전트) **ESP-NOW엔 우선순위/QoS API가 아예 없다는 것**을 확정 —
CHANNEL_PING이 사진 청크 버스트와 같은 TX 큐를 공유해서, 채널은 멀쩡한데 청크가 몰릴 때 PING이
진짜로 큐잉 지연으로 타임아웃(500ms)을 넘겨서 오탐(false-positive 채널 끊김)이 나는 구조였음.
`esp_now_channelsync_notify_alive()`를 추가해서, PONG뿐 아니라 성공한 Layer-1 왕복 응답이면
뭐든 "살아있다는 증거"로 인정하도록 확장 — "로컬 상태를 절대 못 믿고 항상 실제 왕복으로
검증한다"는 원칙은 유지하면서 그 왕복의 종류만 넓힘. 사용자 확인: "가져오기는 매우 안정적
(아직 한번도 에러 없음)".

부수적으로 `ESP_ERR_ESPNOW_NO_MEM`(로컬 큐 꽉 참 — 아예 전송도 안 나간 것)이 PING 실패/reliable
요청 타임아웃으로 잘못 카운트되던 버그 2건도 같이 수정.

### 4. (내 도구 버그) pyserial DTR 리셋 — CNTL "크래시" 오진단

가져오기 테스트 중 CNTL이 리셋된 걸 보고 크래시로 의심했으나, 사용자가 "네가 새로 캡쳐시작한다고
할 떄 리셋했어"로 정정 — pyserial이 포트 열 때 기본으로 DTR=True를 거는 게 ESP32-S3
USB-Serial-JTAG 오토리셋 회로를 건드린 것이었음. `serial_read.py`/`serial_stream.py`(스크래치패드)
전부 열기 전에 `dtr=False; rts=False` 설정하도록 수정. 메모리
`reference_pyserial_dtr_reset_bug` 참고 — 스크래치패드는 세션마다 새로 만들어지니 다음에도
재발 가능, 처음부터 이 패턴 적용할 것.

### 5. 지금촬영 버그(2026-08-02 to-do 1번) — 실은 두 개의 독립된 버그였음

Layer 0/1 실기검증 중 사용자가 자발적으로 재현: 지금촬영 여러 번 반복하면 목록/사진이 이상하게
나옴. "통신 문제 아니니 대화만 이어가겠다"는 사용자 지시로 코드 건드리지 않고 먼저 설명만 들음,
그 다음 화면에 숫자 1/2/3/4를 띄워가며 통제된 재현 테스트로 원인 확정. 자세한 내용은 메모리
[[project-cntl-cam-capture-now-race-and-frame-lag]] 참고.

- **버그 A (Cntl UI)**: 진행팝업 "취소"가 실제 요청 완료를 안 기다리고 바로 배경타이머를 풀어줘서,
  취소 직후 새 선택을 하면 이전 요청의 뒤늦은 응답이 새 선택 위에 잘못 표시될 수 있었음. "취소"를
  소프트 취소(라벨만 "종료 대기 중..."으로 바뀌고 모달은 유지, 실제 완료/8초 타임아웃까지 안 풀림)
  로 바꾸고, READY 소비 지점 2곳을 전부 `consume_ready_photo_if_current()`로 통일 — 선택
  file_id와 도착 file_id가 다르면 화면에 안 그리고 새 에러코드 3008(`UI_ERR_PHOTO_SELECTION_STALE`)
  토스트를 띄움.
- **버그 B (CAM, 더 심각)**: `esp_camera`의 DMA 프레임버퍼 풀(fb_count=2, 이 보드는 OV3660)이
  부팅 직후 딱 2장 채우고는 멈춰버림(누가 `fb_get()`+`fb_return()`으로 안 비우면 ISR이 더 못 찍음).
  촬영할 때마다 딱 1장씩만 갱신되면서 정확히 "요청 2번 전" 프레임이 나오는 구조 — 실기로 숫자
  1/2/3/4 재현해서 정확히 이 패턴 확인(촬영1,2는 부팅시점 옛날 사진, 촬영3,4는 촬영1,2 때 화면).
  파일 mtime은 저장 시점 기준이라 목록 시각은 항상 정상으로 보여서 더 헷갈렸음. 수정:
  `camera_capture_one()`에서 진짜 저장할 프레임을 받기 전에 `CAM_VIDEO_FB_COUNT`만큼 먼저
  버려서 큐를 신선하게 만듦 — OV5640(fb_count=1)도 같은 매크로라 자동으로 맞게 동작.
  **참고**: 이 버그는 자동촬영(3/10시간 간격 등)에도 똑같이 적용되던 함수라, 그동안의 자동촬영
  사진들도 촬영시각 표기 대비 내용물이 fb_count주기만큼 밀려있었을 가능성이 높음(과거 데이터
  자체를 다시 볼 계획이 있다면 참고).
