### 6. Layer 2 — Selective Repeat(SR) 청크 전송 설계+구현+실측비교+적용

사용자가 원래 계획대로("SR 구현 → SR 30분 BMT → 현재방식 30분 BMT → 비교 → 적용") 끝까지
진행. 자세한 기술 내용은 메모리 `project_cntl_cam_esp_now_reliability_layers` 참고, 요약만:

- **설계**: CAM이 16개 청크씩 윈도우 단위로 보내고, 윈도우 끝날 때마다 그 범위만 Cntl한테
  물어봐서(새 메시지 `PHOTO_WINDOW_STATUS_REQUEST`/`_ACK`) 누락분만 즉시 메꿈. 기존
  `resend_chunks()`/`esp_now_reliable_request()`를 거의 그대로 재사용해서 새 코드는 최소화.
  끝에 기존 DONE/DONE_ACK/NACK라운드 안전망은 그대로 유지.
- **벤치마크 구현 중 실버그 발견**: `s_photo_cam_mac`(Cntl이 응답 보낼 대상)이 Cntl이 먼저
  요청할 때만 채워지던 변수였는데, 벤치마크는 CAM이 요청 없이 먼저 미는 구조라 이게 항상
  0(빈 MAC)이라 응답이 전부 `ESP_ERR_ESPNOW_NOT_FOUND`로 실패하고 있었음. `handle_meta()`가
  실제 발신자 MAC으로 갱신하도록 고쳐서 해결 — 이건 원래 코드의 잠재적 결함이 아니라 벤치마크
  설계(CAM 선요청 없이 미는 방식) 자체가 새로 노출시킨 문제였음.
- **30분 실측 비교 결과**(71KB/60청크 파일, 실제 AP 채널, 같은 세션에 연달아 측정):
  - SR: 1696건 완료, 실패 0, 평균 1061ms, **최대 1166ms**
  - 현재 방식: 1593건 완료, 실패 0, 평균 1133ms, **최대 8840ms**
  - 청크 재전송량(리던던시) 자체는 둘 다 미미(SR 0%, 현재방식 약 0.1%) — 진짜 차이는 현재
    방식이 "가끔 파일 끝에서 NACK 라운드가 걸리면 그 한 번이 최대 2.4초×3번씩 늘어지는" 꼬리
    지연시간 문제였고, SR은 그걸 윈도우 단위로 쪼개서 계속 확인하는 구조라 최악의 경우도
    안정적으로 억제됨.
- **프로덕션 적용**: `photo_transfer_task`의 실제 전송 루프를 `send_one_photo()`에서
  `send_one_photo_sr()`로 교체. 실기로 file_id 여러 장 가져오기 재확인 완료(전부 1라운드 만에
  정상 완료).
  **⚠️ 이 전환 도중 한 번 실수로 되돌아갔다가 몇 번의 CAM 재빌드/재플래시를 거치는 동안 원복이
  안 된 채로 남아있었던 적이 있음(git 커밋 분리 작업 중 소스를 임시로 되돌렸다가 다시 적용하는
  걸 깜빡함)** — 최종적으로는 다시 잡아서 고치고 실기로 SR이 실제로 도는 것까지 재확인했지만,
  혹시 다음 세션 시작 시점에 "가져오기가 느린데?" 싶으면 제일 먼저
  `grep -n "send_one_photo_sr(ids" CAM/main/esp_now_cam.c`로 실제 프로덕션 경로가 SR을 쓰고
  있는지부터 확인할 것(빌드된 바이너리 신뢰하지 말고 소스 기준으로).
- 옛 방식(`send_one_photo()`)은 안 지웠음 — `BENCH_START` mode=1(`XFER_BENCH` 현재방식)로 계속
  재현/재비교 가능하게 남겨둠. 벤치마크 트리거 UI 버튼 3개는 결정 다 나고 적용까지 끝나서 제거함
  (아래 8번).

### 7. CAM 이름 유니크성 — MAC 뒤 2바이트 → 3바이트

사용자 지적: 2바이트(65536가지)만으로 이름을 만드는 게 딱히 그럴 이유가 없었음(제조사가 실제로
기기마다 다르게 부여하는 구간은 3바이트=24비트인데 그중 1바이트를 버리고 있었음). MAC 뒤 3바이트
전부 쓰도록 `resolve_name()` 수정(`Cam-XXXXXX` 6자리 hex). 여러 CAM을 실제로 구분해야 하는
상황(아래 9번)이 생기면서 마침 관련성이 생김.

### 8. Cntl 대시보드 — 여러 CAM 선택 드롭다운 (2-CAM UI 백로그 항목 해결)

`s_paired_cam_mac`(자동으로 "테이블에서 처음 걸리는 페어링된 CAM" 하나만 쓰던 전역변수)을
`s_selected_cam_mac`(드롭다운에서 사용자가 고른 CAM)로 교체. 사용자가 대화로 확정한 UX 결정

- **드롭다운은 CAM이 1대뿐이어도 항상 표시**(대수에 따라 UI 형태가 바뀌는 걸 사용자가 명시적으로

이 앱에서 첫 `lv_dropdown` 사용. 자세한 구현 포인트는 메모리 `project_cntl_multi_cam_selector`
참고. 실기 검증 완료(1대 상태에서 드롭다운에 그 하나만 뜨고 자동 목록가져오기 동작 확인).

## 이전 절 (Layer 0/1 + 지금촬영 버그, 이 문서 앞부분에 이미 썼던 내용)

### 1. Layer 0 — 채널 추적(esp_now_channelsync) 구현 + 검증

CHANNEL_PING/PONG 전용 메시지로 채널 추적을 페어링/앱 트래픽과 분리 — 채널이 바뀌어도 재페어링
없이 ~1.2초 안에 재동기화. 채널 강제 전환 테스트로 실기 검증 완료.

### 2. Layer 1 — Reliable 모드(esp_now_reliable) 구현 + 검증

`esp_now_reliable_request()` — 재시도 있는 블로킹 요청/응답. Layer 0 위에 얹음. 페어링/목록/촬영/
삭제 등 제어 메시지에 적용.

### 3. 3006(가져오기 무응답) 재발 — 원인 규명 + notify_alive() 수정

Layer 0/1을 실기 검증하던 중 "20번 정도 가져오기하니까 또 3006" 재현. ESP-IDF v6.0.2 소스를
직접 확인해서(Explore 서브에이전트) **ESP-NOW엔 우선순위/QoS API가 아예 없다는 것**을 확정 —
CHANNEL_PING이 사진 청크 버스트와 같은 TX 큐를 공유해서, 채널은 멀쩡한데 청크가 몰릴 때 PING이
진짜로 큐잉 지연으로 타임아웃(500ms)을 넘겨서 오탐(false-positive 채널 끊김)이 나는 구조였음.
`esp_now_channelsync_notify_alive()`를 추가해서, PONG뿐 아니라 성공한 Layer-1 왕복 응답이면
뭐든 "살아있다는 증거"로 인정하도록 확장.

### 4. (내 도구 버그) pyserial DTR 리셋 — CNTL "크래시" 오진단

pyserial이 포트 열 때 기본으로 DTR=True를 거는 게 ESP32-S3 USB-Serial-JTAG 오토리셋 회로를
건드린 것이었음. `serial_read.py`/`serial_stream.py`(스크래치패드) 전부 열기 전에
`dtr=False; rts=False` 설정하도록 수정. 메모리 `reference_pyserial_dtr_reset_bug` 참고 —
스크래치패드는 세션마다 새로 만들어지니 다음에도 재발 가능, 처음부터 이 패턴 적용할 것.

### 5. 지금촬영 버그(2026-08-02 to-do 1번) — 실은 두 개의 독립된 버그였음

- **버그 A (Cntl UI)**: 진행팝업 "취소"가 실제 요청 완료를 안 기다리고 바로 배경타이머를 풀어줘서
